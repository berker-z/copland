# copland

A personal dashboard and project tracker that runs on your own Cloudflare account. Boards and tasks, which you can share with friends and hand to AI agents, with your calendar, notes and inbox beside them, and crypto prices, the weather and the moon if you want them.

It's the successor to [nord-dash](https://github.com/berker-z/nord-dash) (the look, the panes, the themes) built on the backend of a task tracker I wrote for work (the Worker, sign-in, live updates). The name is Copland OS from Serial Experiments Lain, since nord-dash was already "the Wired".

**Status:** early, but usable locally. The backbone works: sign-in, invites, per-user settings, the encrypted key vault, and live updates between tabs and between people. Every nord-dash pane is ported: calendar and agenda (Google or any ICS link), tasks, markets, notepad, and the statusline weather. Which panes and statusline items are on, and where, is yours to arrange on a map of the dashboard (settings › widgets, or the customize button in the statusline): one to three columns, drag panes between them, drag widgets in from a tray to switch them on and back out to switch them off. Markets, weather and the moon start off. A new dashboard has three columns, /wired and /nudge on the left, then boards, tasks and inbox, then agenda, calendar and notepad. /wired is your agents' work drawn as the pole from the logo and its wires (more under Agents), and /nudge a list of the agents you may message, to send one a line. The tracker has boards you can share, a kanban with drag and drop, a list view, a Gantt you can drag bars on, labels, comments, editable stages, planning (epics, milestones, parent tasks, dependencies) on every board, with three dots on each card saying where it sits and a parent's progress (`3/7`) beside them, filters over all three views (level, a task's subtree, assignee, labels, text, and closed tasks only from the last two weeks unless you ask) that live in the URL so a filtered board is a link, a link for every task (`/b/BOARD?task=KEY`, the board with that task open), swimlanes by epic on the kanban, and per-board notes and docs for whoever works there, agents included. It works on a phone (a swipeable board, long-press to move a task) and installs to the home screen. Claude and other AI assistants can connect over MCP. See [TODO.md](TODO.md).

## How it fits together

One Cloudflare Worker serves everything. The React app is static assets on the same Worker; `/api/*`, `/auth/*`, and the MCP server and its OAuth (`/mcp`, `/oauth/*`, `/.well-known/*`) go to the Worker code. There is no separate backend.

- **D1** (Cloudflare's SQLite) holds users, sessions, settings, boards and tasks. Schema in [migrations/](migrations/). The Worker's five-minute cron also clears out rows nothing reads any more, a few hundred per table per tick (`src/worker/housekeeping.ts`): expired sessions and OAuth codes, runs ended over 30 days ago, tokens revoked or expired over 30 days ago that no kept run uses, and the changed-files lists of tasks closed or deleted over a week ago. Device requests are tidied on the same cron.
- **A Durable Object per user** holds that user's open tabs as WebSockets, and the daemon's, which connect with a token and land in the hub of whoever the token is (an agent's token, the agent's own). After a write succeeds, the Worker tells the affected users' hubs which topics changed, and their tabs refetch. Your settings change reaches your other tabs; a task moved on a shared board reaches everyone on the board. Messages carry topic names only, never data, so a refetch still goes through the normal access checks.
- **Google** is used for sign-in (OpenID Connect with PKCE, done server-side; sessions are our own cookie, stored hashed) and, separately and optionally, for calendars. Connecting a calendar is a second consent asking for calendar scopes; the Worker keeps the refresh token encrypted and calls Google itself, so the browser never holds a Google token. Calendars can also come from any ICS link, which the Worker fetches and expands (repeating events, exceptions, time zones). People go by a handle they choose (`@sam`, unique on the instance), made from their Google name when the account is created; the name itself is not kept, and a picture is one they upload, not Google's.
- **GitHub** comes in through a GitHub App of the instance's own, which an admin makes in two clicks from settings (GitHub's manifest flow) and installs on their repos. It only reads. Its webhook tells the Worker about branches, PRs and CI, which show up on the tasks whose keys they name, and a merged PR that closes a task moves it to done. Details in [docs/GITHUB.md](docs/GITHUB.md).
- **API keys** people add in settings (CoinGecko) are encrypted with AES-GCM under a Worker secret and never sent back to the browser. The Worker calls those services on the user's behalf. CoinGecko answers are cached for fifteen minutes, since the free plan is rate limited. Services that need no key (Binance prices, Open-Meteo weather and city search) are called straight from the browser.

Data comes in two kinds. Personal things (settings, keys, notes, calendar connections) are only ever visible to their owner. Boards have members with roles (owner, editor, viewer), and every board route checks membership first. Your private todo list is just a board with one member, your inbox; a project with a friend is the same thing with two.

The code is split by runtime: `src/worker` runs on Cloudflare, `src/app`, `src/features`, `src/lib` and `src/ui` run in the browser, and `src/domain` is plain TypeScript both sides import (types, settings shapes, live topics). Three tsconfigs keep them from sharing globals by accident.

## Connecting an AI assistant

Copland has an MCP server at `/mcp`, so Claude (or anything else that speaks MCP) can read and change your boards: "what's due this week?", "move LNCH-4 to done", "put a passport renewal in my inbox for the 20th". Settings › access has the URL, the steps and what is connected as you. A task you create through it without naming a board goes in your inbox; an agent always names one, `"inbox"` for its owner's, and is refused without it.

- **claude.ai and the Claude app:** Settings › Connectors, add a custom connector with `https://<your-host>/mcp`, press connect. You sign in to Copland if you aren't already, see a consent page, and pick who it connects as (you, one of your agents, or a new agent) and read and write or read only.
- **Claude Code:** `claude mcp add --transport http copland https://<your-host>/mcp`, then `/mcp` inside Claude Code to sign in the same way.
- **Anything else:** make a personal token in settings (`cpl_…`, shown once) and send it as `Authorization: Bearer <token>`. The same token works on `/api` directly, for scripts.

Whatever connects as you acts as you and nothing more: it gets your role on each board, and a task's history says "berker-z via Claude Code". The tools don't touch the database. They call the app's own API routes in-process as you (`src/worker/mcp.ts`), so the access checks, validation, event log and live updates are the same ones the browser goes through. A read-only token is refused on any write, on `/mcp` and `/api` alike. `/mcp` only takes tokens, never the session cookie, so another site can't drive it through your open tab.

The OAuth side (`src/worker/oauth.ts`) is the minimum MCP clients need: protected-resource and authorization-server metadata, dynamic client registration, public clients with PKCE only, and refresh tokens that rotate on use. Tokens of both kinds live in `api_tokens` as hashes, and stop working the moment their owner is disabled. Settings lists them with when each was last used, and revokes them.

### Agents

An assistant can also be an agent: a name of its own like `berker-z/codex`, made in settings › agents or right on the consent page. Tasks are assigned to it, history says what it did, and it starts with nothing. You put it on the boards it should work on, never above your own role or editor, choose whether anyone but you can give it work, and tick which of your own notes and calendar it may read, and whether it may write your notes. Over the MCP that is `list_events`, and `list_notes`, `read_note`, `write_note` and `delete_note`; without the grant they refuse and say who would have to give it. `write_note` replaces a note's whole text or appends to it, and can take the `updated` value `read_note` returned (`base_updated`) so it refuses rather than overwrite a note that changed in between (the notepad itself is last-save-wins). Pause it and its tokens stop; delete it and its name is free again while its history stays.

Work happens in runs. Whatever launches an agent's runtime (a daemon, a script) starts a run with the agent's token (`POST /api/runs`) and hands the runtime the run's own secret instead, so every change it makes lands in history with the run: "dev via Codex · run 8f31". Any call keeps the run alive; ten minutes of silence and it shows as stale, and nothing has to notice a crash. A run takes a task with `claim_task`, which assigns it if nobody has it, moves it to an active stage and puts "dev is on this · run 8f31" on the card. Only one run holds a task at a time, and the claim lapses with the run. A launched run that fails or goes quiet puts its task back in todo, where the next run picks it up in the same worktree; three dead runs in a row and it goes to blocked for a person instead. A chat session (Claude Code, Codex in a terminal) claims the same way without a launcher: its first claim makes an interactive run for its connection, any call with that connection keeps it alive, and the card says "dev is on this · Claude Code". Claude Code can keep it alive between Copland calls with a hook that calls the MCP's `heartbeat` on every tool use, and the same hook brings the run any comment or mention on its task at its next step, so a question from the owner reaches it while it works (COPL-139; the daemon's runs get the hook too); this repo has one in `.claude/settings.json`, and the snippet to copy is in [docs/AGENT-IDENTITIES.md](docs/AGENT-IDENTITIES.md#interactive-runs). The agent's settings page lists its latest runs, each with how it ended when its launcher said ("exit 1 after 3.8s"), and a run that put a task back says the same in the task's history. The details are in [docs/AGENT-IDENTITIES.md](docs/AGENT-IDENTITIES.md#runs-and-claims). The design is in [docs/AGENT-IDENTITIES.md](docs/AGENT-IDENTITIES.md), and where it is all going in [docs/DIRECTION.md](docs/DIRECTION.md).

While a run holds a coding task, the daemon reports what the task's worktree has changed (`PUT /api/tasks/:id/files` with `{ base, files }`, `src/worker/routes/files.ts`). Only the run holding the task's live claim can, with its run's secret; Copland keeps the latest list per task, up to 500 paths, so open tasks that change the same files can be shown side by side. A task's summary then says which other open tasks on its board share files with it and how many (`overlap: [{ key, files }]`), and `GET /api/tasks/:id/overlap`, the MCP's `overlap` tool, says which files, who is on each and when each was reported; the guide has leads sequence or merge overlapping work and agents fetch early. On the board, a card that overlaps shows a muted file icon with how many tasks, and the task modal lists them with the shared paths. It's information, not a lock. See [docs/GITHUB.md](docs/GITHUB.md#overlap-work-still-in-flight).

The /wired pane draws all of this. Four poles in a row, each with its list underneath: todo, doing, then blocked half a span on and done a span on. Doing forks by span: a short wire to blocked, and a long one that sags under blocked and rises to done. Each task your agents have is a bead in its stage colour. What waits sits on the wire into doing; a task a run has claimed sits at the doing pole with current running along its wire and a timer in the list (the status strip has it when the list is too narrow); blocked ones wait, blinking, on the short wire by the blocked pole; done ones ride the long wire to done and fade off the edge, and the list keeps the last 24 hours. An active task no run holds (an agent working without a run, or a run that died) still counts as doing, dimmer and without a timer. When a task moves, its bead travels the wires to its new pole. The pane reads `GET /api/wired`, yours only (`src/worker/routes/wired.ts`). It is all Copland's own data (assignments, stages, claims), so it works without the daemon. With no agents it says how to make one.

Anyone, person or agent, has an inbox. Being given a task by someone else, or `@mentioned` in a comment, lands there, and so does a new comment on a task you take part in (you made it, are assigned to it, commented on it or were mentioned on it): in the /inbox pane on your dashboard and behind the bell in the statusline on every screen, where you can open or dismiss each item, and through the MCP's `inbox` tool for an agent. Opening a task in the browser, from the inbox, the board, a link or the box's bell, marks your unread items on it read (given, mentioned, commented), so reading a mention on the task clears it everywhere; a message about the task stays unread until you read it in the inbox, since it is not part of the task's page (`src/domain/inbox.ts`). Agents mark their own items read through the MCP: nothing on the server marks anything read because a task was fetched. It comes a page at a time, newest first, and an agent can ask for only the unread and follow a cursor to older pages, so unread work is never stuck behind fifty read items (`GET /api/inbox?unread=true&limit=&cursor=`, in `src/worker/routes/inbox.ts`). Marking something read twice is harmless. A handle inside code (inline or a fenced block) or on a `>` quoted line is talking about someone, not to them, so it notifies nobody; the Worker and the comment highlight share that rule (`src/domain/mentions.ts`). Mentions are matched against the board's members when the comment is written and kept by id, so renaming someone never moves a mention.

A message is a short note for what isn't a task's discussion: "you forgot the README on COPL-42", "look at COPL-55 next". It lands in the recipient's inbox, about a task or about nothing in particular (`POST /api/messages`, `src/worker/routes/messages.ts`; the MCP's `send_message`). You can message your own agents, and an agent can message you. Someone else on a board an agent is on can message it only when you let the board's members give it work, and the agent treats that as untrusted, like a comment; yours count as your requests. A reply goes back to whoever sent the message it answers. Agents don't message other agents, and people talk to each other in comments. Who may message whom is `src/domain/messages.ts`. In the browser you message an agent from the /nudge pane on your dashboard: it lists everyone you may message (your own agents first, then others' agents opened to a board you share; `GET /api/messages/recipients`, held to the same rule as sending), and picking one opens a line under it. Each says whether its box is on, that is whether the daemon running it is connected to Copland's live updates (a socket opened with one of the agent's tokens that pinged within the last 75 seconds; `connectedPrincipals` in `src/worker/live.ts`), since nothing reads a message while it is off; stopping an agent is the pause button on its settings page, not a message. You answer a message from the inbox, where "reply" opens one line under it. From the box, `m` on an agent in its agents screen sends one, and the bell lists your agents' messages with mentions and blocks, each one markable read. An agent run by the daemon wakes on a message: every message, about a task or not, gets a short message run of its own that claims it first and doesn't code, a run on a task handles only that task's comments and mentions, and a message that comes while a run is going waits for the next (`daemon/README.md`, Messages). A run claims a message before acting on it, like a task (`POST /api/messages/:id/claim`, the MCP's `claim_message`): one live claim per message, so two runs never answer the same one, and the claim ends with the run or when the message is marked read. See [docs/AGENT-IDENTITIES.md](docs/AGENT-IDENTITIES.md#runs-and-claims).

A stage's name is the board's own business; its category is what it means, and that is what agents go by. In flow order: `backlog` is parked, `todo` is ready to be picked up, `active` means someone is on it, `blocked` is waiting on a person, and `done` and `cancelled` close the task. An agent takes work from todo stages or what is assigned to it, and leaves backlog alone unless asked. When it needs an answer it comments with an @mention and moves the task to the board's blocked stage, then back to an active one once answered. A new board starts with backlog, todo, doing, blocked and done; an inbox keeps todo, doing and done. A new task without a stage lands in the first todo stage (on a board without one, the first open stage that isn't backlog), from the app and the MCP alike (`defaultStage` in `src/domain/tasks.ts`).

A parent's stage follows its children, so nobody moves an epic by hand. When a child goes active or blocked, a parent sitting in backlog, todo or a closed stage moves to the board's first active stage. When a child finishes and every child is then closed, at least one of them done, an open parent moves to the first done stage. A child parked in backlog is still open work and holds its parent open; work that is really dropped gets cancelled or deleted. Only a child finishing closes a parent: adding, moving or deleting a child never does. A child put back in todo under a closed parent reopens it to todo. Children that are all cancelled leave the parent alone, a parent already active or blocked is never moved back, and a parent moved by hand stays put until one of its children changes again. It carries up the tree, so a task can close its story and the story its epic. The Worker does it in the same write as the change that caused it (a move, a new parent, a new child, a deletion), logs each move on the parent as the same person's or agent's change ("moved it to done, following COPL-12"), and returns the parents it moved; the browser applies the same rule to its cache (`followChildren` and `followUp` in `src/domain/tasks.ts`, checked by `npm run check`).

A board can tell its agents how to work there. Its notes (the book icon in the board header, up to 1000 characters of markdown, written by owners and editors) are quoted under that board in the MCP guide, as its conventions for how work is done there: context for the agent, not authority. The guide also gives agents a trust order (the owner and the agent's own description first, then Copland's rules, the user's request, board notes, docs, task briefs, comments, and outside content last), and lower-trust text never widens what an agent may do or gets the owner's notes or calendar shown to people who can't see them. Its docs are reference files: specs, briefs, style guides. They use the same upload and the same R2 key space as task attachments, and the same download route, which lets in whoever is on the board. Viewers read them; editors add, describe and remove them. An assistant never gets a doc's contents unasked. The guide lists each doc by name, type, size, date and one line (the description someone gave it, or for a text doc its first heading or opening), and `read_doc` fetches one when the work calls for it. Text docs (markdown, plain text, CSV) come back as text; a PDF or an image doesn't, and `read_doc` says what it is and gives the link instead. `write_doc` writes a markdown doc from the assistant's side, since it has no file to upload.

A comment can carry images: PNG, JPEG, GIF or WebP, at most six (`src/domain/commentImages.ts`). They are uploaded like any file (`POST /api/uploads`) and their keys sent with the comment (`POST /api/tasks/:id/comments { text, attachments: [key] }`), which takes only the poster's own uploads not yet on anything and writes the comment with all of them or not at all. Each comment in the thread lists its images (`{ id, name, type, size, url }`), served by the same download route as task attachments with the same check, whoever can read the board; they don't show again among the task's own attachments. Editing a comment leaves them alone, and deleting it deletes them, files included. In the browser (`src/features/board/CommentImages.tsx`) they are thumbnails under the comment's text that open full size in the task attachments' viewer. An image pasted into the comment box or dropped on it (or picked, on a phone) uploads at once and waits as a thumbnail you can remove; non-images and anything past the cap are turned away before they upload, with the reason under the box, and posting waits for the uploads. The MCP's `get_task` shows each comment's images by name and link, and `comment_on_task` posts them: `images: [{ name, data }]`, each a PNG or JPEG as base64 (the type read from its bytes, not its name), at most 5 MB decoded, which the tool uploads through the same route as raw bytes before posting the comment with their keys (`RawBody` in `src/worker/mcp.ts`). A bad image refuses the whole comment before anything is uploaded, and a read-only token is refused at the upload. The route is checked end to end on an in-memory database in `checks/comments.check.ts` (`checks/worker.ts` loads Worker modules under node for that), and so is the tool, through `handleMcp`.

`src/worker/mcpCoverage.ts` says, for every API route, which tools use it or why none do. `npm run check` fails when a route has no entry, so a new route can't quietly leave the MCP behind.

### Running agents on your machine

`daemon/` is the Copland daemon, in Rust: `copland-daemon --headless` watches the inboxes of the agents in `~/.config/copland/daemon.toml`, and when a task lands in one it starts a run with that agent's token, claims the task, and launches the configured runtime (Claude Code with `-p`, or any command) with an MCP config that connects it through the run. It finishes the run when the runtime exits, completed on exit 0 and failed otherwise, and failed too when a runtime exits 0 leaving its task in an active stage, as one that ends its turn with work running in the background does (COPL-147); it stops a runtime that is still going after two hours (failed too). A mention on a task that isn't the agent's gets a launch without a claim, to answer there. It only uses the HTTP API. The agent marks its inbox read itself; the daemon remembers what a run already saw so it doesn't relaunch on the same items. Up to ten runs per agent at once: tasks on a board with code (a GitHub repo, or any git remote, no GitHub needed) are coding work, and an agent with a `code_command` does each in the task's own git worktree (`~/copland/work/COPL-79`, kept across runs, on a branch named after the task), inside a sandbox that can only write there, picked by its runtime (`runtime =`, or read off the command): the runtime's own where one is checked (Codex's, which also holds its commands to GitHub and the package registries), bubblewrap on Linux and Seatbelt on macOS for any other, side by side; anything else runs one at a time in the agent's `workdir`. A task is coded; an epic or a story is led: the agent reads the repo and plans it into child tasks with dependencies, which then run by themselves. How to build and configure it is in [daemon/README.md](daemon/README.md).

A box gets its tokens through a device login, so nobody copies a token around (`src/worker/routes/device.ts`, the same shape as OAuth's device flow). The box calls `POST /api/device/start` with no credentials and shows the code it gets back, like `KQ7M-X3TP`, and a link to `/device?code=KQ7M-X3TP`. You open it signed in, check the code matches the box's screen, tick which of your agents it may run, and approve. That makes ordinary tokens: a read-only one for you ("lain box"), so the box can draw your agents' work, and a read and write one for each ticked agent ("lain"), so it can start their runs. They show up in settings as "Copland box" and are revoked there like any other. Meanwhile the box polls `POST /api/device/poll` with a long device code only it has, and gets the secrets exactly once; they wait sealed under `VAULT_KEY` until then. A code lasts ten minutes, and an approval nobody collects in that time loses its tokens. Approving needs your session: a token, even yours, is refused on it. The two open routes are capped per IP and in total. A box that already runs some agents asks for one more the same way from its agents screen, naming it in `agents` on the start (handles or ids, optional); the approval page then ticks exactly those to begin with, and you can still change it (migration 0017). Sending a message or marking your inbox read from the box are writes, which its read-only token can't do, so the first time you try it asks for a read and write token for you alone with `write: true` on the start: the page then lists no agents and says what that token can do, and approving makes only it ("lain box, messages"), which the box keeps beside the read-only one (migration 0026).

## One instance, several people

The first person to sign in on a fresh instance gets in without an invite and is its admin. After that, the `SIGNUP` var decides who gets an account:

- `invite` (default): admins make invite links in settings. A board's share button finds people already here by handle; for someone who isn't here yet, "invite by email" at the bottom of it makes a link that brings them straight onto that board.
- `open`: anyone with a Google account.
- `closed`: nobody new. This is the setting for a copy that's just for you: sign in first, and the door shuts behind you.

Admins make other people admins (or stop them being one) and disable accounts in settings › instance. There is always at least one admin; the last one can't step down. Being an admin is about the instance, not your data: it doesn't let anyone read other people's boards or notes.

If you lock yourself out anyway, `npm run admin -- you@example.com` makes an existing account an admin directly in D1. It needs Wrangler logged in to the instance's Cloudflare account, which is the real proof that it's yours.

## Running it locally

```sh
npm install
cp .dev.vars.example .dev.vars   # then fill in VAULT_KEY and DEV_USER_EMAIL
npm run db:migrate
npm run dev
```

With `DEV_USER_EMAIL` set, localhost requests without a session act as that user (created as an admin the first time), so you don't need Google set up to work on it. It is ignored for any host other than localhost.

## Deploying your own

You need a Cloudflare account and a Google Cloud project for the sign-in client.

1. `npx wrangler login`, into the account you want this on.
2. `npx wrangler d1 create copland` and put the `database_id` it prints into `wrangler.jsonc`.
3. In Google Cloud, create an OAuth client (type "Web application") with the redirect URI `https://<your-worker-host>/auth/callback`. Put its client id in `GOOGLE_CLIENT_ID` in `wrangler.jsonc`.
4. Set `SIGNUP` in `wrangler.jsonc`.
5. Secrets:
   ```sh
   npx wrangler secret put GOOGLE_CLIENT_SECRET
   openssl rand -base64 32 | npx wrangler secret put VAULT_KEY
   ```
   Keep a copy of the vault key. Lose it and every saved API key has to be entered again.
6. `npm run deploy`, which builds, applies migrations to the remote database and deploys. Then sign in straight away: the first account is the admin.
7. Optional: deploy on every push to main. `.github/workflows/deploy.yml` runs the same `npm run deploy`. Make a Cloudflare API token from the "Edit Cloudflare Workers" template, add Account › D1 › Edit, and save it in the GitHub repo as the `CLOUDFLARE_API_TOKEN` secret, with your account id (`npx wrangler whoami`) as `CLOUDFLARE_ACCOUNT_ID`.
8. Optional: GitHub. Signed in as the admin, settings › instance › github › create GitHub App, confirm on GitHub, and pick the repos it may read. Nothing to set in Cloudflare; its key is kept under `VAULT_KEY`.

Both sign-in and the calendar connection come back to the same `/auth/callback`, so the OAuth client needs one redirect URI per host. For calendars, enable the Google Calendar API in the same Google Cloud project. Sign-in only asks for name and email, which needs no verification from Google. The calendar scopes are "sensitive": until the app is verified, people see an "unverified app" warning and click through it, and there is a 100-user cap, which is fine for friends. Publish the consent screen (In production) either way; while it is in Testing, Google expires refresh tokens after 7 days.
