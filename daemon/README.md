# copland-daemon

The thing that runs your Copland agents on your own machine. It watches each agent's inbox, and when a task lands there it starts a run, claims the task, and launches whatever runtime you configured (Claude Code, a script) with an MCP config that connects it to Copland through that run. When the runtime exits, the daemon finishes the run. This is COPL-9: headless only, one runtime binding (a local command), deliberately plain.

It talks to Copland only over the HTTP API, with each agent's own token, like any other client. Nothing here touches the database, so the access checks, the event log and live updates are the Worker's as usual.

## The loop

Per agent, every `poll_interval` seconds:

1. Read the agent's unread inbox (`GET /api/inbox?unread=true`, following `next`).
2. Drop items the agent wrote itself (by the actor's id against the token's, from `/api/me`), except `unblocked` ones, and set aside every message, about a task or not (see Messages). Group the rest by task, oldest first. Then add the agent's ready work (`GET /api/tasks/ready`, COPL-86): tasks assigned to it, in a todo stage, every dependency closed, nobody's run on them, and not part of an open story the agent is assigned to (the story is offered instead, as a lane, COPL-235). Nothing in the inbox says so when a task the agent gave itself can start; Copland decides it, and the daemon only asks. A task whose last open dependency closes (or is deleted) is in the inbox as well, as an `unblocked` item for each assignee (COPL-164): the wake guard needs it, since a claim refused as `waiting` is remembered and the dependency closing changes nothing on the task itself. It counts even when the agent closed the dependency itself.
3. For each task that needs it (see the wake guard below), as far as `max_runs` and its account's `max_runs_per_account` allow: `POST /api/runs` with the agent's token, which gives a run and its secret (`cplr_…`). It names the runtime account as a hash, with this daemon's cap (`{ account, account_cap }`, COPL-234), and Copland refuses it with `account_full` while the account's runs going on all the owner's machines are at the cap: then nothing is claimed and the task waits for the next poll (see the account paragraph below).
4. With the run's secret, `POST /api/tasks/:id/claim`. That assigns the task if nobody has it and moves it to the board's first active stage. A refusal is a 409 whose `code` says why, and the daemon goes by it:
   - `claimed`: another run holds it. The daemon finishes its own run as cancelled and comes back once that claim is gone (see the wake guard).
   - `lane`: it is a story's task, and another run holds the story as a lane (COPL-236). The same as `claimed`: the daemon comes back once neither the task nor the story has a live claim.
   - `assigned_elsewhere`: it's someone else's. If an unread item is a mention or a comment, the daemon launches anyway, through the same run but without a claim, with a prompt that says so: "You are @owner/name. You were mentioned on KEY, which isn't yours. Read it with get_task, answer in its comments, and don't take it over." A bare assignment the agent has since lost is skipped.
   - `closed`: launched the same way only when the agent was mentioned, so chatter on finished work doesn't start anything. Otherwise skipped.
5. Write a temporary MCP config (mode 0600, under `$XDG_RUNTIME_DIR/copland/`) pointing at `<url>/mcp` with `Authorization: Bearer <run secret>`, and spawn the command in the working directory with a one-line prompt: "You are @owner/name working on KEY. Read it with get_task, and work as the copland guide says. When you stop, leave the task in the right stage. This run handles only KEY: its comments and mentions. Leave everything else in your inbox unread, messages above all, for the runs they belong to." The guide carries everything else.
6. While the runtime lives, `GET /api/runs/:id` with the run's secret every two minutes, since the lease is ten. If that secret stops working (the runtime called `finish_run` itself), the keepalives stop. A coding worker (or lane) also reports its worktree's changed files every three minutes and once more when the runtime exits, before the run is finished (see Coding tasks).
7. A runtime still going after two hours is stopped the way shutdown stops one (SIGTERM to its process group, SIGKILL ten seconds later) and its run finishes as failed. The ceiling is a constant, not a setting. When the runtime exits, `POST /api/runs/:id/finish` with the agent's token: exit 0 is completed, a runtime that couldn't be started interrupted (no strike, see below), anything else failed. Exit 0 is not enough on its own for a run that claimed its task (COPL-147): a runtime's turn ending is its run ending, so one that ended its turn with work going in the background ("I'll pick it up from there") exited 0 with nothing left to come back. The daemon reads the task first (`GET /api/tasks/:id`, and its board's stages from `GET /api/boards/:id/shell`), and when it is still in an active stage the run finishes as failed, with the reason `ended with the task still active`, which puts it back in todo for the next run in the same worktree and counts toward the three in a row that send it to blocked. If the runtime let the task go (`release_task`), the daemon claims it again with the run's secret first, since only what a run holds is put back. These are ways to stop, never failed (`agent::unfinished`): the task closed, blocked, or back in todo or backlog; another run holding it now; a task that is planned rather than coded (an epic, a story, a milestone, a task with children, and every lead's run); for a lane's run (COPL-236), every task it holds besides its story that is in none of those states, so a lane that leaves one of its story's tasks active and claimed is failed with `ended with the task still active (KEY)`, which puts that task and the story back in todo while the tasks it closed stay done, and one that leaves none active isn't; `review_first` with an open PR (a draft too) left for a person, or `review_first` on a repo without PRs, where the pushed branch is what it leaves; and a task or board that can't be read. Nor does a run wait on a person's merge (COPL-193): while a worker runs on a repo with PRs, the daemon reads its task every minute (`GET /api/tasks/:id`), and once it has seen the task start waiting for review during the run (`review_first`, open, with an open or draft PR, none of which it was at the first look), a runtime still going five minutes later is stopped the same way and its run finishes as completed, with the reason `stopped with its PR open for review after …`. Bringing main into the PR is then left to whoever merges it, or to a later run a comment wakes. A PR already open when the run started (a run woken by a comment on it) starts no clock: that run is answering a person, and ends its turn when it has. The clock goes when the task stops waiting (merged, closed, `review_first` turned off) and starts again if it waits again; a task that can't be read leaves it as it was. A runtime that finished its run itself as completed keeps that status, since a finished run can't be finished again. The finish carries how the runtime ended as its `reason` (COPL-136): `exit 1 after 3.8s`, `signal 9 after 12m 4s`, `stopped at the run ceiling after 2h 0m`, `did not start: bwrap: No such file or directory (os error 2)`, at most 160 characters and never anything from the log. Copland shows it on the run in settings and in the history of a task the run puts back. If the runtime already finished the run, its own status stands. The MCP config is deleted.
8. The loop polls again as soon as a run ends.

Steps 2 to 7 are one run, and runs go on their own: an agent can have up to `max_runs` going at once (coding tasks side by side, see Coding tasks), and different agents run side by side too.

The poll is the fallback, not the usual way in (COPL-62). Each agent also keeps a WebSocket open to `/api/live` with its own token, sent as a Bearer header on the upgrade like any other request, never in the URL. The server puts that socket in the agent's own live hub, the one the web app's tabs use, so it hears what is sent to the agent and nothing of its owner's. Messages are topic names, and for a board change which board and tasks (COPL-151: `core/src/live.rs` `Event`, every field past the topics optional, so an older server works the same). An `inbox` one makes the loop poll at once, 300 ms after the first of a burst so a burst is one poll; a `board` one does too, at most every five seconds since busy boards send plenty: a board change can make work ready, or end the wait on a task or a claim the guard remembers. A new assignment starts its runtime about half a second after it's made, where the poll alone took 15 seconds on average and up to 30.

While the socket is up the daemon still polls every five minutes (or `poll_interval`, if that's longer), because the hub keeps nothing and a message sent during a reconnect is gone. When it drops, the daemon polls once straight away and then every `poll_interval` until it's back. Reconnecting backs off from one second to a minute with jitter; a refusal (a 4xx, say a revoked token) waits five minutes. After a reconnect it polls once, for whatever it missed. It pings every 30 seconds and treats 75 seconds of silence as a dead connection. The client is `core/src/live.rs`: the handshake and the frame format by hand over reqwest's upgraded connection, with `ring` (already there for TLS) for SHA-1 and randomness, so no WebSocket crate. Revoking the token, pausing the agent or disabling its owner closes the socket at the next message for it. `AgentState::live` says where each socket is.

The runtime's stdout and stderr go to `$XDG_STATE_HOME/copland/runs/<run-id>.log` (`~/.local/state/copland/runs/` by default), mode 0600. The daemon writes two header lines first (`# copland-daemon: run …` and `# argv: …`) and, whatever the ending, success included, a last line with how it ended: `# copland-daemon: exit 1 after 3.8s`, the same words as the finish's reason. A runtime's stdout goes through the daemon on its way there, a line at a time: Claude Code's result (the one line of JSON `--output-format json` makes it end with) goes in as the text it would have printed without the flag, followed by `# usage: $0.84 · 1.3M tokens (in 12k, out 3.1k, cache read 1.2M, cache write 40k) · 23 turns · 4m 2s`, and everything else as it is (`core/src/usage.rs`, COPL-71). Those numbers go to Copland with the run's finish (`usage` in `POST /api/runs/:id/finish`), even when the runtime finished its run first, and Copland shows them on the run in Settings and sums them on its task, and a parent's subtree, next to progress. They are the tokens of every model the run used (a subagent's too), fresh input, output, read from the cache and written to it, and Claude Code's own cost in dollars. Codex reports its usage only in `codex exec --json`'s event stream, which would make the log unreadable, so a Codex run sends none yet. Once the runtime exits its stdout is read for five more seconds at most, since something it left running can hold it open. The runtime also gets `COPLAND_URL`, `COPLAND_TASK` (the key; not for a run on messages), `COPLAND_RUN` (the id) and `COPLAND_MCP_CONFIG` in its environment. Never the secret; that lives only in the config file.

SIGINT or SIGTERM stops polling, sends SIGTERM to each runtime's process group (SIGKILL ten seconds later), and finishes their runs as interrupted (`cancelled` with `interrupted: true`), which puts their tasks back in todo for the next start. A run stopped from the box is plain cancelled, and Copland parks its task in backlog; one whose runtime fails, failed, which puts it back in todo, or in blocked after three in a row. A runtime that can't be started at all is the machine's trouble, not the task's, so that run finishes as interrupted and costs the task no strike. So is a runtime out of usage (COPL-195, `core/src/limit.rs`): its account has hit its limit, and every run until the reset would exit at once. When a runtime exits non-zero and one of the last eight lines it wrote says so (Claude Code's "You've hit your session limit · resets 8:10pm (Europe/Istanbul)", "… limit reached ∙ resets 3pm", "usage limit reached|<unix time>", in its JSON result or plain; Codex's "You've hit your usage limit … try again at Oct 27th, 2026 3:38 PM" or "… try again in 2 hours"; never a rate limit), its run finishes as interrupted with the reason `out of usage, exit 1 after 3.8s: <what it said>`, the daemon doesn't remember what the run woke for, and the agent is held on this machine (as by `hold`, below) until the reset, and so is every other agent of this daemon on the same runtime account (COPL-232), since they would run out the same way. A clock time is read in this machine's time zone, the one the runtime printed it in; a reset that doesn't read, is past or is more than eight days off isn't trusted, and with none the hold is a back-off instead: 15 minutes, doubled each time after up to an hour, and back to 15 once a runtime runs without running out. Runs going on the same account run out too and say the same; a later reset moves the hold on. At the reset the loop polls at once and picks the work up again by itself; `copland-daemon release` (or the socket's `release`) ends the hold sooner. The box says "‖ out of usage until 17:10 UTC" on the agent's line rather than a failure, and `status` the same. A second signal exits at once; whatever runs were left go stale within the lease, and Copland's cron ends them and puts their tasks back.

When Copland is down (COPL-148): a poll that gets no answer, or a 502, 503 or 504 (a D1 failure is a 503 `storage_unavailable`), starts no run and claims nothing until a poll gets through. The log says it once, `Copland unavailable since 23:20 UTC`, and so does the agent's line in the box, over a run that is going; a later poll that gets through says it is back. Runtimes already going are left alone. A run's last words, its finish and its worker's last files report, are asked again while Copland is down: from 5 seconds, doubling to 5 minutes between tries, for up to a day (`Backoff::LAST_WORD`, `core/src/api.rs`), and once more on shutdown before giving up. A refusal ends that at once. If the outage outlasted the lease, Copland's cron has ended the run as stale by the time the finish lands; Copland then takes the finish's ending instead of the cron's failed, so the run costs its task no strike (docs/AGENT-IDENTITIES.md).

## The wake guard

The agent marks its inbox read itself, over the MCP, because only it knows what it dealt with. The daemon marks something read only when nothing could ever answer it (a closed task, below), so it needs its own way of not relaunching forever on items a run has already seen:

- After a run on a task (a failed one, or one stopped at the ceiling, included), or a refused claim, it remembers the unread items it had for that task and the task's `updatedAt` as the run left it.
- On later polls, if every unread item for that task is one it remembers and the task's `updatedAt` hasn't moved, it leaves the task alone.
- A newer inbox item for the task, or any change to the task, wakes it again. An `unblocked` item is how a task the claim refused as `waiting` wakes once what it waited on closes.
- A claim refused because another run holds the task is remembered as held. On each poll the daemon reads the task (its summary carries the live claim) and tries again once there is no claim, as long as the agent still has unread items there. While the claim is live, nothing else about the task wakes it.
- A claim refused as `lane` (a story's task, the story held by another run as a lane, COPL-236) is remembered as held the same way, and the daemon also reads the task's parent: it tries again once neither the task nor the story has a live claim, since between tasks the lane run holds only the story.
- A claim refused because the task is closed (409 `closed`) launches a run only for a mention, which answers in the comments without a claim and marks it read itself. Anything else there (an assignment, a comment, an `unblocked` item) has nothing left to answer, so the daemon marks those items read itself (`POST /api/inbox/read`, COPL-165). Before, they stayed unread and every start of the daemon woke for them again, a claim refused per item per start.
- Once a task has nothing unread, its memory is dropped.

This applies to failed runs too, so a runtime that crashes on start doesn't get relaunched every 30 seconds. The memory is in-process: restart the daemon and it launches once more for whatever is still unread.

## Messages

A message (COPL-106) is a short note from the agent's owner, or from a board member when the owner lets members give it work, that lands in the agent's inbox with its text and whether it is trusted (from the owner). Every message gets a message run, about a task or not, and no run on a task ever sees one (COPL-127). Before, a message about a task joined that task's wake and every task prompt said "check your inbox", so two coding runs that started a second apart both answered the same message (COPL-123).

- **The batch:** the unread messages that no run holds a live claim on (the inbox item's `message.claim`) and that no run of this daemon has had go to one run, oldest first and at most 20 (the rest go to the next), in `workdir` with no worktree, so it waits while another run has the workdir and counts against `max_runs`.
- **Claimed first:** with the run's secret the daemon claims each message, `POST /api/messages/:id/claim` (COPL-124), before it launches anything. One refused, because another run claimed it first (409 `claimed`) or it was read since the inbox was read (409 `read`), is left out of the batch and logged; a batch left empty finishes its run as cancelled and launches nothing. So two runs, two daemons on one agent token, or a chat session never handle the same message: only what the run holds is in its prompt. The claims end with the run, released by its finish.
- **The prompt** quotes each message, with who sent it, whether it is the owner's request or untrusted, the key of the task it is about when it names one, and its message and inbox item ids. It says to answer each with `send_message { reply_to }`, not a comment, then `mark_read` it; that a message about a task is about that task (read it, comment on it or change it when asked); that "on <name>" names one of the agent's boards, even one called like the app; and to put work that needs more than an answer on the board as a task assigned to the agent, naming its board, which gets a run of its own. It doesn't code. `COPLAND_TASK` is not set, and the run shows in `AgentState::runs` under the task `messages` (`runner::MESSAGES`).
- **Task runs** handle only their own task's comments and mentions; their prompts say so, and to leave the rest of the inbox, messages above all, unread for the runs they belong to.
- **Timing:** the daemon puts nothing into a runtime that is already going. A message that comes during a run waits for the next message run. `AgentState::messages` counts the messages that are waiting like that (no run has had them, none is on them and no other run holds them), for the box to say so. Comments and mentions on a task a run is working on are different (COPL-139): Claude Code's heartbeat hook, which both of setup's Claude Code commands carry in `--settings` (the examples below have it), brings them into the conversation at the run's next step, through the MCP and with no part for the daemon. Without the hook the run sees them when it reads the task again, which the guide has it do before it integrates.

The claim is what keeps two runs apart; the guard still remembers each message a run of this daemon claimed, by inbox item id and whatever the run's ending, because the claim ends with the run: without it, a message the run finished with but left unread would be free again at once and launch run after run. A new message launches one for itself, and a message's memory goes once it is read. Another daemon on the same token remembers nothing of it, so it may take such a message once, after the run that had it is over.

## Config

`~/.config/copland/daemon.toml` (`$XDG_CONFIG_HOME/copland/daemon.toml`), or `--config <file>`. Unknown keys are refused. `copland-daemon --setup` writes one for you on a terminal (see Setting it up on a terminal), and `copland-box --setup` in its window (see "Setting it up" under the box); this is what it writes, with the `code_command`, `writable` and `runtime` under Coding tasks, and how to write it by hand.

```toml
poll_interval = 30   # seconds while the live socket is down; optional, 30 by default

[[agent]]
url = "https://copland.example.com"
handle = "berker-z/dev"            # for display; the token's own handle is what counts
token_file = "~/.config/copland/dev.token"
workdir = "~/work/dev"
client = "Claude Code"             # optional; history says "via Claude Code"
command = [
  "claude", "-p", "{prompt}", "--output-format", "json",
  "--mcp-config", "{mcp_config}", "--strict-mcp-config",
  "--tools", "",
  "--permission-mode", "dontAsk",
  "--no-session-persistence",
  "--settings", '{"attribution":{"commit":"","pr":""},"hooks":{"PostToolUse":[{"matcher":"^(?!mcp__copland__)","hooks":[{"type":"mcp_tool","server":"copland","tool":"heartbeat","input":{"event":"${hook_event_name}"},"timeout":10}]}],"UserPromptSubmit":[{"hooks":[{"type":"mcp_tool","server":"copland","tool":"heartbeat","input":{"event":"${hook_event_name}"},"timeout":10}]}]}}',
  "--allowedTools",
  "mcp__copland__guide", "mcp__copland__whoami", "mcp__copland__get_task",
  "mcp__copland__list_tasks", "mcp__copland__my_work",
  "mcp__copland__inbox", "mcp__copland__mark_read",
  "mcp__copland__claim_task", "mcp__copland__release_task", "mcp__copland__finish_run",
  "mcp__copland__comment_on_task", "mcp__copland__move_task", "mcp__copland__update_task",
  "mcp__copland__create_task",
]
```

`command` is an argv array, not a shell line, so nothing gets word-split. `{prompt}` and `{mcp_config}` are replaced wherever they appear. The token is an agent's API token (`cpl_…`, made on the agent's page in settings, read and write). Put it in `token_file`; `token = "cpl_…"` inline works too. Either way the daemon warns if the file holding it can be read by anyone but you.

About the Claude Code flags, as of Claude Code 2.1: `--tools ""` takes away every built-in tool (no Bash, no Edit, no file reads), `--strict-mcp-config` ignores your other MCP servers, and `--permission-mode dontAsk` denies whatever isn't in `--allowedTools` instead of waiting for a prompt nobody will answer. `--allowedTools` is variadic, so keep it last. It is narrow on purpose: `command` is for runs with nothing to code (messages, tasks on a board without a repo) and runs outside any sandbox, so Copland's tools are all it gets. Writing code is `code_command`'s (Coding tasks, below), in the task's own worktree inside the sandbox. `claude` has to be signed in already (`claude` once, interactively); the daemon doesn't handle that.

### Coding tasks

A task on a board with code, a GitHub repo or a plain git remote (docs/GITHUB.md), is coding work, and an agent with a `code_command` does it in a workspace of its own instead of `workdir` (`core/src/workspace.rs`). The daemon keeps one clone per repo under `code_dir` and makes the task a git worktree beside it, on a branch named after the task:

```text
~/copland/repos/berker-z/copland     the clone, shared by every task and agent here
~/copland/work/COPL-79               COPL-79's worktree, on copl-79-<its title>
~/copland/work/COPL-227              story COPL-227's lane, on whichever of its tasks' branches it is doing
~/copland/build/berker-z/copland     the repo's build output, shared by its worktrees
```

The worktree belongs to the task, not to a run: a run that crashed, a later run that picks the task up again, and a run fixing what CI found all carry on in the same place on the same branch. A new one starts from the default branch's head as it is right then. If the worktree is gone but the branch is still around, here or on GitHub, it is made again on that branch. Once the task closes, its worktree goes, along with its local branch; the one on GitHub is GitHub's to delete. A run that ends on a closed task removes its own; for a task closed with no run after it, by a person merging its PR or by hand, each agent with a `code_command` sweeps `code_dir/work/` when its loop starts and then every five minutes. It asks Copland about each directory named like a task key and removes the worktree of a task that is closed, or gone from a board the agent is on. It leaves alone a task one of its runs is on, one it can't read (another agent's board answers 404 just like a deleted task does, so a 404 counts as gone only on a board the agent is on), and anything that isn't a worktree named like a key. Agents share `code_dir`, so two sweeps can meet the same closed task; the second finds nothing to do. The clone goes over https, so pushing uses whatever git credential helper the machine has; `gh auth setup-git` is the easy one.

What a coding run costs on disk (COPL-187): the clone once per repo, a worktree per open task, and what its builds make. For Copland's own repo the worktree is small, `node_modules` a few hundred MB, and Cargo's output large: the box, with GPUI, made 6 to 7 GB in each worktree's `daemon/target/`, so four runs going at once took 25 GB. So a worker's run gets `CARGO_TARGET_DIR` set to the repo's shared build dir, `code_dir/build/<repo>`, which the sandbox lets it write besides its worktree, and every worktree of the repo builds into one place. Measured on the headless daemon (`cargo test --no-run` and `cargo clippy --all-targets`) with two checkouts 20 commits apart: each in a target of its own took 1.2 and 1.1 GB, 36 and 35 s; sharing one took 1.5 GB for both, the second built in 14 s, and the first again in 1 s. sccache as `RUSTC_WRAPPER` with a shared cache was the other choice and saved no disk: each target stayed the same size, plus the cache (245 MB), and builds were slower (133 s cold, 89 s warm) since it can't cache incremental crates or clippy's checks. Sharing has its prices: cargo builds one at a time in a target dir (a run waits on "Blocking waiting for file lock on build directory" while another builds), and branches that differ recompile what differs when they take turns. Every cargo workspace in the repo builds there, which is fine: cargo keys what it keeps by package and settings. The shared dir holds no one task's output, so it goes when the repo's last worktree does (the sweep or a run removing it); in between it only grows by what branches compile differently. To start it over, remove it while no run of that repo is building. The preflight warns when `code_dir`'s disk runs low (see Checking a machine).

What the run does follows the task's level (COPL-87). A task, a leaf, is a worker's: it gets the worktree above, codes, and opens one PR. A task directly under an epic is one too. An epic, or a task that has children (the children count `GET /api/tasks/:id` sends a parent), is a lead's: it gets no worktree but the clone itself, checked out at the default branch's head (detached) and read-only in the sandbox, and is told to plan the work into child tasks with `depends_on` where one needs another's result, assign them, and leave the parent open. Children assigned to the agent start by themselves (they are ready work, step 2), side by side up to `max_runs`, each in its own worktree, and the parent closes when they are done. A milestone runs nothing.

A story is a lane (COPL-236, board doc orchestration), with children or without. Its run gets one worktree, `work/<story key>` (`workspace::lane`), made detached at the default branch's head, since no work goes on a branch of the story's own, and found as it was left by a later run of the story. The prompt has it read the story, list its open tasks (`list_tasks { parent }`) and take them in order, after what each depends on and then as they stand on the board, planning them first as the guide's Leading section says (assigned to itself) when there are none. For each in turn it claims the task beside the story, fetches, makes the task's branch from the default branch as it is then (`copl-n-short-title`), does it as the guide's Code section says, one PR with `Fixes KEY` merged once CI is green, and waits for it to land before starting the next. The story stays open and closes when its tasks are done; its worktree goes then, by the run that ends on it or the sweep. The sandbox is a worker's, the worktree and the clone's `.git`, which is where the branches and fetched objects go, so the run fetches, branches and pushes as a worker does. Its changed files are reported against the task it holds at the time (from its run's claims, `GET /api/runs/:id`), each task's from scratch, and none between tasks, so overlap stays per task. It handles comments and mentions on the story and on its tasks, which its prompt says are in its inbox. While a story assigned to the agent is open, its tasks start no runs of their own: their inbox items are left to the lane (one read of the task's parent tells), and Copland doesn't offer them as ready work (COPL-235). A lane keeps no session for a chain (`resume_chains`): its tasks run in one session already. The ceiling and the three strikes hold it as any run.

The run gets `COPLAND_ROLE` (`worker`, `lane` or `lead`) besides the variables below, and `COPLAND_INTEGRATE`: `pull-request` on GitHub, `fast-forward` on a plain remote, whose worker is told to fast-forward `main` and close the task itself. A plain remote's clone goes under `repos/git/<host>/<path>`.

`code_command` runs inside a sandbox (`core/src/sandbox/`), picked by the agent's runtime and the platform (COPL-141): the runtime's own sandbox when it has one we've checked, else the platform's fallback, bubblewrap on Linux and Seatbelt on macOS (COPL-140). Codex has its own (COPL-143, below); Claude Code doesn't yet. The runtime is `runtime = "claude-code"` or `"codex"` on the agent; left out, it's read off `code_command`'s program (`claude`, `codex`, or the name a `sh -c` script is given, as in the box's Codex template), and any other name is an unknown runtime, which gets the fallback. Every backend gets the same list of what a run may write, and one test (`sandbox::conformance`) holds each to it. Everything is readable and nothing writable except the worktree, the clone's `.git` (where the worktree's commits go), the repo's shared build dir (above), a temp dir of the run's own (a fresh empty `/tmp` on Linux; on macOS a directory under the daemon's `$TMPDIR`, the run's `TMPDIR`, removed when the run ends), and what `writable` lists: the runtime's own state and the caches its builds use. The Nix package has bubblewrap built in, by its store path (COPL-137); any other Linux build (cargo, the release tarballs) looks for `bwrap` on PATH, so install bubblewrap for it: the `bubblewrap` package on Arch, Debian, Ubuntu and Fedora. Use the distribution's and not a copy of your own: on Ubuntu 24.04 and later AppArmor limits unprivileged user namespaces, and only the distribution's `bwrap` has the profile that allows them. Without `bwrap` the run doesn't start: every poll, before it starts a run or claims a task, the daemon looks for the programs its runs need (the command's, and for coding runs the sandbox's and the `code_command`'s) on its own PATH, and leaves waiting the runs that would need a missing one. The agent's line in the box says which: "bwrap not found on PATH: coding runs can't start; install the bubblewrap package …". Once the sandbox's program is found, the daemon tries it once (`bwrap --ro-bind / / true`, or an allow-everything profile through `sandbox-exec`), and when that fails the line says what it said and coding runs wait the same way: "bwrap is there but can't make a user namespace (…): coding runs can't start. On Ubuntu 24.04 and later AppArmor allows that only to the distribution's own bwrap …". Restart the daemon after fixing it. When everything is found and works the log says so, with where the sandbox is ("bwrap at /nix/store/…" for the Nix package). A box started from a desktop launcher has the launcher's PATH, which may not be your shell's. Neither fallback limits hosts, so a coding run under one reaches the network the way the machine does, and it can push wherever your git credentials can. On Linux the fallback's run has a process namespace of its own (`--unshare-pid`), so whatever it started, a dev server it left in the background included, ends when the runtime does, however that ends: it doesn't keep running, or hold its port, after the run.

On macOS (`/usr/bin/sandbox-exec`, built in, nothing to install) the profile is `allow default`, then `deny file-write*`, then writes allowed again to the paths above (resolved, since Seatbelt matches real paths: `/var` is `/private/var`) and to the terminal devices and `/dev/null`. The paths go in as `-D` parameters, never spliced into the profile's text. macOS has no process namespaces, so cleanup is the best the platform allows: the runtime stays in the process group the daemon made for it, and when the runtime exits the daemon kills that group, which takes everything it started that is still in it (a server backgrounded with `&` or `nohup` included). What leaves the group itself, with `setsid`, as a Node child spawned `detached` or a server that daemonizes, outlives the run and keeps its port until you stop it. Stopping a run (shutdown, the run ceiling, the box's stop) signals the group as on Linux. `sandbox-exec` has been marked deprecated in its man page since macOS 10.12 and is still what other tools sandbox with there. Nobody has tried any of this on a real Mac yet: `cargo test` on CI's `macos-14` runner (`.github/workflows/daemon-ci.yml`) runs a sandboxed command that writes inside the worktree, its extras and `TMPDIR` and fails to write outside them, and that is the whole of what is known to work.

Codex's runs are sandboxed by Codex itself (`core/src/sandbox/codex.rs`, COPL-143), on Linux with its bubblewrap and seccomp and on macOS with its Seatbelt, since Codex sandboxes the commands it runs and not itself. The daemon doesn't wrap the command; it appends the policy to it as `-c` overrides (`approval_policy="never"`, a permission profile named `copland`, `default_permissions="copland"`, Codex's network proxy) and sets `TMPDIR` to the run's own temp dir, so a Codex `code_command` has to hand what follows its own arguments on to `codex exec`, as the box's template does with `"$@"`. It also has to leave the sandbox to the daemon: the config refuses a Codex `code_command` that says `--sandbox`/`-s` (which turns Codex's permission profiles off), `sandbox_mode`, `--full-auto`, `--add-dir`, `--yolo` or `--dangerously-bypass-approvals-and-sandbox`, and keep `--ignore-user-config`, since a `sandbox_mode` in your `~/.codex/config.toml` does the same. (A system-wide `/etc/codex/config.toml` or managed requirements are Codex's and still apply.) The profile reads everything and writes the worktree, the clone's `.git`, the worktree's own git dir under `.git/worktrees/` (which Codex keeps read-only unless it is named, so commits would fail without it), the run's temp dir and what `writable` lists that exists; a lead's writes none of the repo. Codex's file edits (`apply_patch`) are held to the same paths: Codex refuses an edit outside them ("writing outside of the project"), and applies the rest inside the sandbox. Commands reach the network only through Codex's proxy, which lets through `github.com`, `api.github.com` and `*.githubusercontent.com` (git over https and `gh`, with the machine's credentials), and `registry.npmjs.org`, `index.crates.io` and `static.crates.io` for a fresh worktree's first build, and nothing else: any other host is refused, and so is a connection that goes around the proxy. A remote over ssh, or one that isn't GitHub, can't be pushed to from inside. Codex's own traffic, the model and Copland's MCP over HTTP, is Codex's process, outside the sandbox. Codex runs each command in a sandbox of its own: a dev server and the browser taking screenshots go in one command, and the browser skips the proxy for `localhost` (the proxy refuses local addresses). When the run ends the daemon kills Codex's process group, as on macOS. `cargo test` runs `codex sandbox` with the exact policy the daemon generates (no model needed): the conformance test, Codex's `apply_patch` writing in and failing outside, a commit from a worktree, and the hosts; CI installs Codex 0.159.2 and requires them on Linux and `macos-14`. A real `codex exec` run against Copland with this policy reached the MCP (`whoami`, `get_task`) without asking, committed in its worktree, read GitHub and was refused everywhere else. So the box's Codex `command` is its `code_command` as it is, and setup writes it as both (COPL-160), with `writable` the caches from the list below, `~/.cache`, `~/.npm`, `~/.cargo/registry` and `~/.config/.wrangler`, and `runtime = "codex"`; Codex keeps its own state in `~/.codex`, outside the sandbox, so that needs no place there.

This is what setup writes for a Claude Code agent (`core/src/runtime.rs`, `Runtime::code_command`):

```toml
code_dir = "~/copland"   # top level; optional, ~/copland by default
min_free_gb = 20         # top level; optional: the preflight warns with less free on code_dir's disk
max_runs_per_account = 3 # top level; optional: runs going at once on one runtime account, across the agents, 3 by default

[[agent]]
# ...as above, then:
code_command = [
  "claude", "-p", "{prompt}", "--output-format", "json",
  "--mcp-config", "{mcp_config}", "--strict-mcp-config",
  "--permission-mode", "bypassPermissions",
  "--no-session-persistence",
  "--setting-sources", "project",
  "--settings", '{"sandbox":{"enabled":false},"attribution":{"commit":"","pr":""},"hooks":{"PostToolUse":[{"matcher":"^(?!mcp__copland__)","hooks":[{"type":"mcp_tool","server":"copland","tool":"heartbeat","input":{"event":"${hook_event_name}"},"timeout":10}]}],"UserPromptSubmit":[{"hooks":[{"type":"mcp_tool","server":"copland","tool":"heartbeat","input":{"event":"${hook_event_name}"},"timeout":10}]}]}}',
]
writable = ["~/.claude", "~/.claude.json", "~/.cache", "~/.npm", "~/.cargo/registry", "~/.config/.wrangler"]
runtime = "claude-code"   # optional; read off code_command when left out
max_runs = 10            # optional; this agent's runs going at once, 10 by default
account = "work"         # optional; the runtime account its runs count against, read off the runtime's login when left out
resume_chains = false    # optional, off by default: a chain's next task carries on where the last left off (below)
```

An agent can have several runs going at once, up to `max_runs` (COPL-82). Coding tasks run side by side, each in its own worktree; anything else still shares `workdir`, so only one of those runs at a time. A run that turns out to answer a mention without a claim on a coding task's board also lands in `workdir`, without waiting for it, which is the one way two runs can share it. A task is never in two runs at once, and a reload or shutdown lets every run going finish before the agent hands over.

Every run also counts against its runtime account (COPL-232, `core/src/account.rs`), and the daemon caps runs going at once per account across all its agents: `max_runs_per_account`, top level, 3 by default. An agent's account is its runtime and who is signed in to it, read every poll from the runtime's own files: Claude Code's `oauthAccount.accountUuid` in `.claude.json` (in `$CLAUDE_CONFIG_DIR`, else `$HOME`), Codex's `tokens.account_id` in `auth.json` (in `$CODEX_HOME`, else `~/.codex`). So two agents on one subscription share one account, and two machines signed in to it name the same one with no config. When nothing can be read (an API key login, an unknown runtime) the account is the runtime's name, `claude-code` or `codex`, shared by every agent on that runtime here; `account = "…"` on an `[[agent]]` names it instead, and agents given the same name share it. Who is signed in is personal, so the log and the status show an account as the runtime with a masked email or a short hash, `claude-code (b…@…)`, `codex (3f2a91)`, or the configured name. Before a run starts, its loop takes a seat on the account; the run gives it back when it ends, however it does, interrupted and stopped by hand included. A lane (a story's one run, COPL-236) takes one seat, and so does a run on messages. `max_runs` stays a second limit, the agent's own. Work the account has no seat for is not claimed and no run is started or finished for it, so it stays ready in todo, costs no strike, and starts at the next poll with a seat; a seat going back polls the agents waiting for one at once. While it waits the status says `waiting_for_slot` and the text "waiting for a slot on claude-code (b…@…)". Three is low on purpose: a feature's two to four lanes run side by side, and COPL-195 hit the account's usage limit with ten runs going on one agent. A reload applies a new `max_runs_per_account` from each loop's next poll, rebinding no agent; runs going keep their seats, and with fewer seats than are taken, nothing new starts on that account until enough have ended. A changed `account` rebinds its agent like any other key, after its runs. Copland shares the count across machines (COPL-234): each run is started naming its account and the cap, `POST /api/runs { account, account_cap }`, where `account` is the first 16 hex digits of the SHA-256 of the account's key (`claude-code:<uuid>`, or the configured name), so Copland never sees the runtime's id or an email. Copland counts the live runs on that account (running, and heard from within the run lease) across the owner and every agent of theirs, so a laptop and a desktop signed in to one subscription share one cap, and refuses the start with a 409 `account_full` ("2 runs going on account 3f2a91 (laptop, desktop), at its cap of 2") while they are at it, in one statement, so two daemons racing for the last slot can't both get it. That refusal is the local wait again: nothing is claimed, no run exists to finish, so no strike, the status says "waiting for a slot on …", and the loop asks again a poll interval later (or sooner, when a seat goes back here). An account that is only the runtime's name says nothing about who is signed in, so it is not sent, and stays one machine's count. Each daemon sends its own cap, so two machines with different caps each hold to their own. Settings shows a run's account in short ("on account 3f2a91"). The box shows each run on the scene and in the stop list. A fresh worktree has no `node_modules` or `target`, so a run's first build installs them; sharing them between branches isn't safe, since branches can differ in what they depend on, and npm's and cargo's caches (in `writable`) make it quick.

A chain (COPL-189, `core/src/chain.rs`) is a task that depends on another task of the same agent, on the same board and so the same repo. With `resume_chains = true` on the agent, the next task of a chain starts from where the last one left off instead of cold. Its worktree is the last one's (`workspace::continue_from`): whatever that task left uncommitted is reset and its untracked files cleaned (its work is merged; ignored build output such as `node_modules` stays), it goes onto the new task's branch from the default branch as fetched just then, its old local branch goes, and it moves to `work/<new key>`. That happens only when the new task has no worktree or branch of its own yet, the last task is closed and assigned to the agent, and its worktree is still there; when it depends on several, the one closed last. The new task's run waits for the last one's run to end, which may still be in that worktree. Which task came before is read from the tasks the new one depends on, one `GET /api/tasks/:id` each. To keep the worktree for it, a run ending on a closed task leaves its worktree while an open task waiting on it (not in backlog, sharing an assignee, with no worktree of its own) is there, as `GET /api/tasks/:id/dependents` lists them, and so does every agent's sweep, whatever its own setting: agents share `code_dir`, and with the setting off the waiting task starts in a worktree of its own and the next sweep takes this one. With Claude Code (a `code_command` whose program is `claude` itself) the session carries on too. A worker's run then drops `--no-session-persistence`, so Claude Code keeps its session, and the daemon keeps the session id its result names with the run, in `state_dir/sessions/<KEY>.json`. The next task's run starts with `--resume <id>`, after the daemon copies the session's file (and the folder beside it) to the project folder of the worktree's new place under `~/.claude/projects/` (or `$CLAUDE_CONFIG_DIR`), since Claude Code finds a session by the directory it is resumed in. Its prompt says it is a new task, which task came before, that main has moved since, and that the conversation before it is the last task's, which is closed. Its usage says `resumed` (COPL-71), so resumed runs can be compared with cold ones. Codex runs are `--ephemeral` and resume nothing; they get the worktree alone. A resumed session carries everything the last task did, so every turn of the next is billed on that context and it fills up sooner against the run ceiling: this may cost more than it saves, which is why it is off by default.

While a worker runs, the daemon tells Copland which files its task has changed, so open tasks that change the same files show up before either has a PR (COPL-103, docs/GITHUB.md's Overlap). It lists them in the worktree (`workspace::changed_files`): tracked changes against the merge base with `COPLAND_TARGET`, committed or not (`git diff --name-only <merge base>`), plus untracked files git doesn't ignore (`git ls-files --others --exclude-standard`), sorted, deduplicated and capped at 500 the way Copland keeps them. The merge base, not `COPLAND_BASE`: once the agent merges `origin/main` in, a diff from where it started would count everything main changed. With no merge base, `COPLAND_BASE` stands in. Paths Copland would refuse (control characters, backslashes, over 512 characters) are left out. It sends them with `PUT /api/tasks/:id/files` and the run's secret every three minutes (its own clock, so a large repo doesn't run git every keepalive) and once after the runtime exits, before the run is finished, but only when the list differs from the last one sent. A failed report is logged at `warn` and tried at the next tick; it never fails the run. A refusal (the claim is gone: the task closed or moved to blocked, or the runtime finished the run itself) stops the reports for that run. Before the last one the daemon reads the run (`GET /api/runs/:id`, whose `claims` are the keys it holds) and sends nothing when the task isn't among them or the secret no longer works (COPL-173): a PR merged at the end of the run has closed the task by then, and the report would only be refused. A lead's read-only clone, and a run answering a mention without a claim, report nothing.

Nothing in the daemon is about one runtime. It hands the run the worktree as its working directory, and `COPLAND_REPO`, `COPLAND_WORKDIR`, `COPLAND_BRANCH`, `COPLAND_BASE` (the commit it started from) and `COPLAND_TARGET` (`origin/main`) in its environment. The prompt says which repo, branch and base, and points at the Copland guide's Code section, which says how coding work is finished: commit, push, open a PR with `Fixes COPL-79` in its body, wait for CI, and merge it, unless the task is marked review first. The merge is what closes the task. A runtime started by the daemon still reads its own settings, the ones you use at the keyboard, and those were written for someone sitting there. The Claude Code command above skips Claude's permission prompts (`bypassPermissions`), since nobody is there to answer them and the sandbox is what limits it. But an `ask` rule in your `~/.claude/settings.json` (say, before `git push`) still asks, and in a headless run that is a refusal; and Claude's own sandbox, if you have it on, runs inside ours, where the push fails and the retry outside it asks too. So `--setting-sources project` loads only the repo's checked-in `.claude/settings.json`, not your personal ones (your `CLAUDE.md` still applies), and `--settings` turns Claude's sandbox off, ours being the one that counts. Another runtime needs the same two things in whatever form it takes them: no prompts, and none of its keyboard settings.

Some top-level keys are for the box alone, and the headless daemon ignores them. The menu's settings and boards panels write the first five for you (see "The menu"); a key at its default is left out.

```toml
theme = "nord"                                  # one of Copland's seven themes, or "copland" for yours there
motion = false                                  # a still picture: no sway, current, blinking or travel
notifications = false                           # no desktop notifications (the bell still counts)
compact = true                                  # the status line alone, in a small window
boards = ["COPL", "HOME"]                       # only these boards' tickets on the scene; all by default
owner_token_file = "~/.config/copland/me.token" # your own token, for all four poles (below)
owner_write_token_file = "~/.config/copland/me.write.token" # yours too, read and write: messaging your agents (below)
owner_url = "https://copland.example.com"       # only when the agents are on more than one Copland
```

`owner_token_file` (or `owner_token = "cpl_…"` inline) is a token of yours, the person the agents belong to, made in settings › tokens; read-only is enough and is what to use. It is held to the same rules as the agents' tokens: an API token, never a run's secret, with a warning if the file can be read by anyone but you. It is for one Copland: the agents' `url` when they all share one, else `owner_url`, which a config with agents on more than one instance must give.

`owner_write_token_file` (or `owner_write_token` inline) is a second token of yours, read and write, for what the box writes as you: a message to one of your agents and your inbox marked read (COPL-109). It comes with `owner_token_file` or not at all, and is for the same Copland. You don't make it by hand: the first time you message an agent from the agents screen, the box asks for it with a device login of its own (below), keeps it in `me.write.token` beside the config (0600) and adds the key. The read-only token stays what it reads with; only someone who wants to write from the box holds a write token on disk, and it can do anything you can. One Copland refuses is forgotten (the key and the file go), so the next message asks again.

`copland-daemon --check` reads the config, checks it, prints what each agent would run, and runs the preflight checks below; it exits non-zero when one fails. `--check --fix` then offers the fixes, as below. Among them it asks each instance who the token is and fails on a token it can't use: a read-only one (runs and claims are writes), or a run's secret (`cplr_…`) given in place of the agent's own token. The daemon checks the same at startup, through `/api/me`'s `access`, and stops watching that agent with an error; when no agent is left it exits. `COPLAND_LOG=debug` shows each poll's decisions and keepalives.

### Setting it up on a terminal

`copland-daemon --setup [--config FILE] [--url ADDRESS]` is the box's setup without a window (COPL-177), for a machine with no display: plain questions on stdin and stdout, Enter taking the default in brackets. It runs only on a terminal; with stdin piped or redirected it refuses and says how to run it. It writes the same `daemon.toml` the box does, with the same core code (`core/src/setup.rs`), so either can set up over the other; `cli/src/setup.rs` asks the questions.

1. **Address.** `--url` gives it, else it asks, and asks again on an address that isn't one (normalized as in the box's setup) or a server that isn't a Copland.
2. **Approve.** It asks for a device code and prints the link and the code to check there, without opening a browser (the machine may have none; open the link anywhere you are signed in). It polls every `interval` seconds, five more each time the server says to slow down, until `expires_in` runs out. Denied or expired asks whether to try again; a poll that fails for a reason that may pass (the network) says so and goes on. The approval page names it `copland-daemon on <host>`.
3. **Tokens.** Saved the moment they arrive, beside the config, with the note `daemon.toml.setup`, as in the box. A setup stopped from here on (ctrl+c, no runtime found, a workdir it can't make) picks up at the runtimes next time, from either program; delete the note to start over.
4. **Runtimes.** It lists `claude` and `codex` as found on PATH with their versions, then asks per agent for one, by number or name (Enter: the first found, Claude Code before Codex, as the box does), and for its workdir (Enter: `~/agents/<name>`). With none found it says what to install and stops.
5. **Save and check.** It writes `daemon.toml`, keeping one already there as `daemon.toml.bak` (or `.bak.2`, …), makes the workdirs, runs the preflight on it and offers each failing check's fix, as `--check --fix` does. On Linux, when a `copland-tray` is on PATH or beside the daemon, it asks first whether to start the tray at login (Enter: no; without `$DISPLAY` or `$WAYLAND_DISPLAY` the question says there is no display here) and writes or removes its autostart entry (see `copland-tray` below). Then whether to start the daemon at login (COPL-223; Enter: no, since a workstation starts it by hand; on a machine that looks headless, with neither display variable or over SSH, `$SSH_CONNECTION` or `$SSH_TTY`, the question says yes is usual there). Yes installs the service with `--autostart` once the config is written (Server mode, below), and says what it did or why it couldn't. It ends saying to connect your own Claude Code or claude.ai to `<url>/mcp` as "you", and, when the answer was no, how to start the daemon by hand: `copland-daemon start` or the Copland Daemon launcher, `copland-daemon` in a terminal, `--install-service` for a service still started by hand, and `--install-service --autostart` for a server. Under Nix (the binary in the store, see Server mode) it asks neither and writes nothing; it ends instead with the home-manager module to add (`services.copland`, with `tray.enable` in a graphical session, and `autostart = true` on a headless machine, a comment saying when to set it elsewhere), or, when the module's unit is there already, with `systemctl --user restart copland-daemon.service` to start it on the new config. The config's header says the same: one written by `copland-daemon --setup` points at `--setup` and `--install-service`, one written by the box at its agents screen.

### One daemon per config

A config is run by one process at a time: `copland-daemon` takes an exclusive `flock` on `$XDG_RUNTIME_DIR/copland/daemon-<hash>.lock` before starting the agents, the hash a SHA-256 of the config's canonical path, and hold it while they run. A second start on the same config stops there with `a daemon is already running <config> (pid N, copland-daemon); stop it, or give this one a config of its own with --config` and exits non-zero. The box runs no agents (it is a client of the daemon, see The box), so it takes no lock: another daemon on its config is simply the one it draws. The kernel lets the lock go when the holder exits or crashes, so there is never a stale one to clean up; the file only holds the holder's pid and binary. Without `XDG_RUNTIME_DIR` (macOS, some sessions) it goes where the MCP configs go, the temp dir. `--check` doesn't take it. `copland_daemon_core::lock::running` says whether a config is being run, and by whom, without taking it (`core/src/lock.rs`).

### Server mode

The box isn't needed to run agents: on a machine with no display (a server, a VM, a spare laptop with its lid shut) the headless daemon does it alone, as a service of yours (COPL-180).

**Workstation or server** (COPL-223). Nothing starts the daemon at login unless you ask for it. On a workstation, a laptop above all, it runs when you start it: the "Copland Daemon" launcher (`release/copland-daemon.desktop`, in the Linux tarball and the Nix package, with a Stop action) runs `copland-daemon start`, which starts the installed service (and the tray's unit, when the home-manager module made one) or, with no service, a daemon on the config until you log out (`service::spawn_session`); `copland-daemon stop` (the launcher's Stop) stops whichever runs the config, and the tray showing it, its unit or one started otherwise (COPL-224), as the tray's Quit Copland does. On a workstation the tray is Copland (COPL-225): its daemon goes when the tray does, by the menu or any other way. The box's offer starts it too. A server or a headless machine asks for it to start at login: `copland-daemon --install-service --autostart` (`--enable` is the same), or the module's `autostart = true;`, with `sudo loginctl enable-linger $USER` so it starts at boot and runs with nobody logged in. In order:

1. **Install** `copland-daemon`: the Linux tarball's `bin/` in `~/.local/bin` (Getting it, below; the window's libraries aren't needed for it), or the Nix package. On macOS, the bare binaries' tarball.
2. **Set it up:** `copland-daemon --setup` (Setting it up on a terminal, above). Open the link it prints on any machine where you are signed in to Copland.
3. **Run it as a service:** with Nix and home-manager, the flake's module does it (`services.copland`, under "Installing it" below). A `copland-daemon` from the Nix store (it, or what its link resolves to, such as a profile's `bin/copland-daemon`, is under `/nix/store` or `$NIX_STORE`: `service::nix_managed`) writes and removes nothing on `--install-service` or `--uninstall-service`: it says the service is home-manager's, prints the flake input, the import and the `services.copland` lines to add (`configFile` when the config isn't the default, `tray.enable` in a graphical session), and exits 1. A unit an earlier `--install-service` wrote at `~/.config/systemd/user/copland-daemon.service` (a file, not home-manager's link) is left where it is and named, with the command that removes it, since home-manager's switch won't replace it. Elsewhere, `copland-daemon --install-service [--autostart] [--config FILE]`. It refuses without a config, pointing at `--setup`, and checks the config loads. On Linux it writes a systemd user unit, `$XDG_CONFIG_HOME/systemd/user/copland-daemon.service`, then `systemctl --user daemon-reload`, `disable` (or `enable` with `--autostart`) and `restart` (so installing again replaces the one running). The unit keeps its `[Install]` section (`WantedBy=default.target`) either way, so `--autostart` only enables it; installing again without `--autostart` turns an earlier one's start at login off. On macOS it writes a launchd agent, `~/Library/LaunchAgents/dev.berkerz.copland.daemon.plist`, loads it with `launchctl bootstrap gui/<uid>` (out first, when it was loaded) and starts it with `launchctl kickstart`. launchd loads every agent there at login, but runs it then only with `RunAtLoad`, which `--autostart` sets along with `KeepAlive` (`SuccessfulExit` false: again after a failure); without it neither is in the plist, since `SuccessfulExit` implies `RunAtLoad`, so a daemon started by hand on macOS isn't restarted after a failure. Either way it is started now. Either runs this binary (`std::env::current_exe`) with `--headless --config <the config, absolute>`, and nothing else: no `PATH` is written into it (COPL-216). That binary has to be somewhere it stays (COPL-219 on Linux, COPL-221 on macOS, `core/src/stable.rs`): `~/.local/bin`, `/usr/bin`, `/usr/local/bin`, `/opt/homebrew/bin`, on macOS an app right in `/Applications` or `~/Applications` (`Copland.app/Contents/MacOS/copland-daemon`), or anywhere else that isn't one of the places that don't last, which are refused before anything is written. Those are a temporary directory (`/tmp`, `/var/tmp`, `/dev/shm`, `$TMPDIR`), a download directory (`~/Downloads`, and `XDG_DOWNLOAD_DIR` from the environment or `user-dirs.dirs`), a cargo `target/`, and a directory below your home whose name has a version in it (`copland-box-0.5.0-linux-x86_64`, `0.5.0`); on macOS also `/var/folders` (where `$TMPDIR` is), a mounted disk or disk image (`/Volumes/…`, gone once it is ejected) and an App Translocation path (the copy macOS runs a quarantined app from when it is opened where it was downloaded). The refusal says where the binary is, why that place won't last, and the command that installs it: for an app, `ditto <the app> /Applications/Copland.app && /Applications/Copland.app/Contents/MacOS/copland-daemon --install-service` (a translocated one doesn't say where the original is, so it says to move it to Applications in the Finder); otherwise to `~/.local/bin`, `cd <the tarball> && mkdir -p ~/.local && cp -r --remove-destination bin share ~/.local/` from an unpacked Linux tarball (`mkdir`, since a new account may have no `~/.local` yet, and `cp` won't make it), an `install -m 755 … ~/.local/bin/` of the binaries beside it otherwise (the macOS tarball's). It doesn't copy anything itself. Run `--install-service` again from where it went after that. Installing again is idempotent. A unit that is already what it would write is left as it is ("already this; left as it is"). One that runs another program, such as a tarball directory you've since deleted, is replaced, and the output names the program it ran. Either way the service is restarted, which starts the binary now on disk; on macOS the plist is read the same way (its `ProgramArguments[0]`, `plist_program`), and the agent is booted out and bootstrapped again, so the file loaded is the one on disk. CI's `macos-14` runner does all of this for real (`release/check-launchd.sh`): both plists pass `plutil -lint`, `--install-service` from `~/.local/bin` shows up in `launchctl print gui/<uid>/dev.berkerz.copland.daemon` with a pid and `RunAtLoad` false, a second install leaves it alone, a stale plist is replaced, `--autostart` sets `RunAtLoad` and installing without it clears it, `stop` boots the agent out and `start` loads and starts it again, one from a temp dir is refused without touching the plist, `--check` names the program, and `--uninstall-service` takes it out. Upgrading in place is copying a newer tarball's `bin/` over `~/.local/bin` again (`--remove-destination`, since a plain `cp` over a running binary fails with "Text file busy"). The unit stays the same, and `--check` says the version of the binary it runs and, when the daemon running is an older one, that `systemctl --user restart copland-daemon` (on macOS `launchctl kickstart -k gui/$(id -u)/dev.berkerz.copland.daemon`) starts the new one. It restarts after a failure, ten seconds apart, and not after a clean stop. Stopping it sends SIGTERM to the daemon alone (`KillMode=mixed`), which stops its runtimes and finishes their runs as interrupted, as ctrl+c does. `systemctl --user reload copland-daemon` has it read its config again (`copland-daemon reload`, under "Status").
4. **Keep it running.** On a server, install it with `--autostart`. A user's systemd services stop when the user's last session ends; on a server you aren't logged in to, `sudo loginctl enable-linger $USER` keeps them running and starts them at boot. `--install-service --autostart` says so when lingering is off.
5. **Read its log:** `journalctl --user -u copland-daemon -f`. The daemon logs to stderr without colour when that isn't a terminal, which is how the journal gets it. On macOS it goes to `~/Library/Logs/copland-daemon.log`. `COPLAND_LOG=debug` in the unit (`systemctl --user edit copland-daemon`, `Environment=COPLAND_LOG=debug`) shows each poll.

**Proved on CI** (COPL-220): the `linux-install` job in `.github/workflows/daemon-ci.yml` builds `copland-daemon` once and runs `daemon/ci/install-flow.sh` with it, the install as `release/INSTALL-linux.txt` has a user do it, from a HOME with no Copland in it. The copy in an unpacked tarball's `bin/` (below HOME, named for a version) and one in a temporary directory are refused and write nothing; the copy in `~/.local/bin` (`mkdir -p ~/.local && cp -r --remove-destination bin share ~/.local/`) writes a unit whose `ExecStart` and `ExecReload` run it, with no `PATH` in it and every other line the shipped unit's. `systemd-analyze verify --user` passes on it and on the shipped `release/copland-daemon.service` (`%h/.local/bin`), where systemd-analyze is installed. Run again, it leaves the unit as it is, with the same contents and modification time. A unit that runs a program that is gone is replaced, and the output names that program. `--check`, on a `PATH` without `~/.local/bin` or `~/.npm-global/bin`, finds stub `claude` and `codex` there and says what the unit runs. It runs on the runner as a new user with a real systemd user manager (lingering on), so the service is started too: not enabled after `--install-service`, enabled after `--install-service --autostart` (the unit itself unchanged), not enabled again after another plain install, stopped by `copland-daemon stop` and started by `copland-daemon start`, then removed, and in `archlinux:latest` (what Omarchy is built on), `fedora:latest` and `ubuntu:24.04` containers. Those have no user manager: Arch has a `systemctl` with no manager to reach, and Fedora and Ubuntu have no `systemctl` at all. So there `--install-service`, with `--autostart` or without, writes the unit and exits 1 saying it couldn't start it. That message says what became of the unit as a successful install does ("Wrote …", "… is already this", "Replaced …, which ran …"). systemd-analyze runs on the runner and in Arch. The script runs anywhere with bash and coreutils: on a machine of your own, give it a scratch `HOME` and an empty `XDG_RUNTIME_DIR`, so it can't reach your own user manager.

A second daemon, or the box, started on the same config while the service runs finds the running one and stops with `a daemon is already running …` (One daemon per config, above): stop the service first (`copland-daemon stop`), or give the other a config of its own. `--install-service` notes it when the config is being run already; the service then retries until that one stops. `copland-daemon --uninstall-service` stops, disables and removes it (`systemctl --user disable --now`, `launchctl bootout`). There is one service per user: installing with another `--config` replaces it.

The service code is core's (`core/src/service.rs`, COPL-199), so the box can install one too: `install` takes the program to run (the CLI passes itself) and whether it starts at login, and returns what it did, the file written and notes such as the lingering one, which `--install-service` prints; for a program in the Nix store it fails first, before looking at the config, with `NixManaged`, which says what to add. The rendering is pure (`systemd_unit` and `launchd_plist`, with tests). The release ships what they render: `release/copland-daemon.service`, for `~/.local/bin` (`ExecStart=%h/.local/bin/copland-daemon --headless`), in the Linux tarball under `share/systemd/user/` and in the Nix package with its store path in `ExecStart`; and `release/dev.berkerz.copland.daemon.plist` in the macOS tarball, a template whose `@DAEMON@` and `@LOG@` are the two absolute paths launchd needs, rendered without `RunAtLoad` (started by hand). A test fails when they differ from the functions. A unit installed by hand from those files is the same as one `--install-service` writes, and finds the runtimes the same way ("Where runtimes are found", below). Under Nix the flake's module installs it (`services.copland`, under "Installing it"), whose unit is the shipped one with the package's binary, and which `nix flake check ./daemon` holds to it.

**Where runtimes are found** (COPL-216, `core/src/search_path.rs`). The daemon looks its runtimes up on `PATH` (`claude`, `codex`, an unknown runtime's program, and git, gh and bwrap), and builds that `PATH` once when it starts (`--headless`, so the service and a daemon started by hand alike, and `--check`), rather than having it frozen into the service at install: a runtime installed or moved later is found at the next start, and a Nix store path is never written down to go stale. In order, each directory once, relative and missing ones dropped: the `PATH` it was started with (so one declared for the service wins), then your login shell's (`$SHELL`, else your passwd entry's, run as `$SHELL -l -c` printing its `PATH` between marks, so whatever your profile prints is ignored; given five seconds, then killed and left out), then `~/.local/bin`, `~/.npm-global/bin`, `~/.cargo/bin`, `~/.bun/bin`, `/usr/local/bin` and, on macOS, `/opt/homebrew/bin`. It is set for the whole process, so runs and the sandboxes' lookups see the same one, and logged once at start (`runtimes are looked up on`). `--check` prints it, with where each program was found or that it wasn't, before its checks. A runtime in none of those places still needs a full path in `command`.

For a program that isn't the daemon (the box, when no daemon runs its config), core has the rest (COPL-199). `service::installed()` says whether there is a `copland-daemon` service, so a config with no service can be told from a stopped service. On Linux it asks `systemctl --user show copland-daemon.service`, which finds the unit wherever systemd loads it from (the one `--install-service` writes, home-manager's link into the store, one under `/etc`), and reads whether it is enabled (starts at login), whether it is running, the program its `ExecStart` runs (`unit_program`), and whether that is in the Nix store (the module's); with no user manager to ask, it looks for `--install-service`'s file. On macOS a plist there is always loaded at login and starts at login when it has `RunAtLoad` (`plist_at_login`), whether it runs is `lock::running`'s to say, and the program is its `ProgramArguments[0]` (`plist_program`). `copland-daemon --check` prints it as its first line after the agents: `service: managed by Nix, starts at login, running (<file>)`, `installed, started by hand, not running: `copland-daemon start` starts it …`, or none, with `--install-service` to get one, or under Nix the module to add. For a service that isn't Nix's, the next line says what it runs (`service::program_says`): the program and its `--version`, or that it isn't there any more; that it is somewhere that won't last, when it is; and, when the daemon holding the config's lock says another version (the lock file's third line, COPL-219), that a restart starts the one on disk. `service::start()` starts an installed one (`systemctl --user start`, `launchctl kickstart`, or `bootstrap` and `kickstart` after a `bootout`), and `service::tray` starts or stops the module's tray unit when there is one: `copland-daemon start` and `stop` are these. `service::daemon_binary()` finds the `copland-daemon` beside the running executable, since the two ship together (the tarballs, the macOS app's `Contents/MacOS`, the Nix package's `bin`), else the first on `PATH`, and says so when there is none. `service::spawn_session(config)` starts `copland-daemon --headless --config <config>` for this session only: in a session of its own (`setsid`), stdin from `/dev/null` and its output appended to `$XDG_STATE_HOME/copland/daemon.log`, so closing whatever started it doesn't stop it. It blocks until the daemon's status socket answers a status request, up to 15 seconds; a daemon that exits first fails it with its exit status and the last lines it logged, one that never answers is killed (it would hold the config's lock unseen) and says so, and a config being run already is refused before anything starts. It isn't a service: it doesn't start at login.

### Checking a machine

The preflight (`core/src/preflight.rs`, COPL-161) says whether this machine can run its agents before a run finds out. `copland-daemon --check` and `copland-box --check` (no window) both run it and print one line per check, `✓` ok, `!` worth a look, `✗` failed, with the fix under each that isn't ok; either exits non-zero when one failed. `copland-box --check` starts with the line `log: <path>`, where the box's own log is (see "Its log"). `--check --fix`, on either, then goes through the ones with a fix it can run, shows what it would run and asks y/N on the terminal for each, runs the ones you say yes to with the terminal handed to them (a login can open a browser or ask things), and checks again. Every program a check starts gets ten seconds, and nothing printed holds a secret.

- **The runtimes**, once each however many agents use one: `command`'s, and `code_command`'s. Claude Code's `claude` must be on PATH and `claude auth status` say `"loggedIn": true` (exit 0); Codex's `codex` on PATH and `codex login status` exit 0. Fix: `claude auth login` or `codex login`; for a missing one, how to install it. A runtime Copland doesn't know is only looked for on PATH.
- **git**: on PATH, with `user.name` and `user.email` in the global or system config, which every commit a coding run makes needs. Fix: asks for them and sets them with `git config --global`.
- **github**: git can reach GitHub over https without asking. It asks git's credential helper for a github.com login the way a push would (`git credential fill`, with `GIT_TERMINAL_PROMPT=0`, no askpass and `credential.interactive=false`), so what it says is what a run's push gets; only the username is shown. `gh auth status` alone wouldn't do: gh can be logged in with git not using it, and another helper (libsecret, osxkeychain) can hold the login without gh. Fix, with gh on PATH: `gh auth login --hostname github.com --git-protocol https` and `gh auth setup-git`; without it, where to get gh.
- **code_dir**: there, a directory, writable, and a git worktree can be made in it: a throwaway repo with one empty commit (an identity of its own, no signing, no hooks) and a worktree of it, in a `.copland-check-…` directory inside, removed after. One that isn't there yet but can be made only warns. Fix: makes it.
- **disk**: `code_dir`'s filesystem (or, while it isn't there yet, the one it would be made on) has `min_free_gb` free, 20 GB unless the config says. Below that it warns, with the five biggest things under `code_dir`: each task's worktree (`work/COPL-12`), the clones (`repos`) and the shared build output (`build`), each as `du` counts it, hard links once, in at most ten seconds. Fix: none to run; it says what can go.
- **token @agent**: each agent's token, asked who it is (`whoami`, as above). Fix: none to run; `copland-daemon --setup` or `copland-box --setup` approves this machine again.

With no agent that has a `code_command`, nothing clones or commits, so git, github and code_dir only warn when they would fail.

**Each board repo** (COPL-178) is checked by the daemon itself, not by `--check`: whether this machine can clone it and push to it, as a coding run would (`preflight::repo_access`). Clone is `git ls-remote <remote> HEAD`; push is `git push --dry-run` of a throwaway empty commit, made in a temp dir, to `refs/heads/copland-push-check`, which connects as a push does (so a remote that would refuse it, GitHub's 403 for a login without write access, says so) and sends nothing and makes no branch. GitHub and plain git remotes get the same check. Prompts are off as for github above, each git gets ten seconds, and a login in a URL is taken out of what it says. An agent with a `code_command` checks every repo on its boards when its loop starts, and a repo it hasn't checked yet (a board's repos changed) when a task on it comes up, not every poll; a failed one is checked again when a task on it comes up ten minutes or more later, so a fixed login is picked up without a restart. It doesn't claim a task (a worker's) on a repo it can't push to, or lead one on a repo it can't clone: the task stays in todo, unclaimed, for a machine that can, the log says why, and `copland-daemon status` lists the repo under `repos` and in `needs`. Each result is `{ repo, clone, push, detail }`, the host report's `RepoCapability`.

**The host** (COPL-179). Each agent's loop tells Copland where it runs, with the agent's own token (`PUT /api/hosts/self`, `api::HostReport`): the hostname (`setup::host`, lowercased; a machine without a usable one reports nothing and names no host), the daemon's version, its runtimes (`command`'s and `code_command`'s, each on PATH and logged in as `--check` finds them, `preflight::runtime_capabilities`) and the board repos above, as checked so far (at most 64). It reports when the loop starts and again whenever any of that changes, and only then: the hostname is read every poll, the runtimes are checked again every ten minutes, and a repo when its check does. A report Copland is down for is asked again with the backoff a run's finish has; one it refuses is logged and left until the report changes. A person's token reports nothing. Every run the loop starts names the host (`POST /api/runs { host }`), and so does its live socket's upgrade (`x-copland-host`), so Copland can tell an agent live on two machines at once.

### Screenshots

A coding run can start Copland's dev server and take screenshots of it in a headless browser, inside the sandbox, to see a UI change before it opens the PR (COPL-120). The daemon needs nothing for it beyond the `writable` above, and `daemon.toml` has no setting for it:

- **The browser** is whichever Chrome or Chromium is on the daemon's `PATH`, which the run inherits (`google-chrome`, or `chromium` from nixpkgs). It isn't in the flake's dev shell: a box from the package doesn't go through that shell, and Chromium is far too big to make everyone building the box download it. Playwright isn't needed; its downloaded browsers don't run on NixOS without nix-ld anyway.
- **Chrome's own sandbox works under ours.** Unprivileged user namespaces nest, so its renderers still get their own user and process namespaces and seccomp, and it needs no `--no-sandbox`.
- **Writable paths:** the profile goes in the run's fresh `/tmp` (`--user-data-dir`), so nothing of the browser's needs to be in `writable`. Chrome still tries `~/.config/google-chrome` and `~/.pki/nssdb`, logs that they are read-only, and carries on. Wrangler keeps local D1 and R2 in the worktree's `.wrangler/`, and its own state in `~/.config/.wrangler`, which the example lists; vite's cache is in `node_modules/.vite`.
- **Ports:** the network is the machine's, so runs side by side share `localhost`. Vite moves to the next free port when 5173 is taken, and the Cloudflare plugin does the same with its inspector port, so read the URL from the log rather than assuming it. The server binds `localhost` only, and ends with the run.

A fresh worktree has no `.dev.vars`; the run writes one (it is gitignored) with a throwaway `VAULT_KEY` and a `DEV_USER_EMAIL`, which signs every localhost request in as that user, and applies the migrations to its own local D1. Then, from the worktree:

```sh
npm ci
printf 'VAULT_KEY=%s\nDEV_USER_EMAIL=dev@example.com\n' "$(head -c 32 /dev/urandom | base64)" > .dev.vars
npm run db:migrate
npx vite > /tmp/dev.log 2>&1 &
until url=$(grep -o -m1 'http://localhost:[0-9]*' /tmp/dev.log); do sleep 1; done
until curl -sf -o /dev/null "$url/api/me"; do sleep 1; done
shot() {
  google-chrome --headless --disable-gpu --no-first-run --disable-crash-reporter --hide-scrollbars \
    --user-data-dir=/tmp/chrome --window-size="$1" --virtual-time-budget=8000 \
    --screenshot="$2" "$url$3" 2>/dev/null
}
shot 1440,900 /tmp/board-desktop.png /b/DEMO
shot 390,844 /tmp/board-390.png /b/DEMO
```

The local database starts empty: the first request makes the dev user, and a board to look at comes from the API (`POST /api/boards`, then `POST /api/boards/:id/tasks`, with `curl` and a JSON body). `--virtual-time-budget` lets the page fetch and render before the shot is taken. 390 is a phone's width, where the board turns into its swipeable mobile layout.

## Status

What the daemon is doing, outside its own process (COPL-170): `Status::of(&DaemonState)` (`core/src/status.rs`, COPL-181) is the daemon's state as JSON, and `Status::render` says it for a person, one block per agent in the box's words. The daemon serves it on the status socket (below), and `copland-daemon status` reads it from a terminal (further below). The box draws from it too (COPL-203): everything the window shows comes from a `Status`, never from `DaemonState`, so what goes through the JSON is all it needs. Since COPL-204 the box gets it from the socket alone (`Watcher`); its tests check that the scene's board and the agents screen come out the same from a `Status` and from that status sent through JSON and back. A field the box needs that `Status` lacks is added here, the add-only way.

The JSON is a contract. `version` is 1; fields are only ever added, never renamed, removed or given another meaning, so a client ignores fields it doesn't know, and a field it needs that is missing means an older daemon. Times are RFC 3339 in UTC, to the second (`2026-10-04T23:20:41Z`); a field with nothing to say is `null`, a list with nothing in it `[]`. The tests in `status.rs` pin every name below.

```jsonc
{
  "version": 1,
  "stopping": false,              // shutdown has begun
  "autostart": false,             // this daemon is the service and starts at login: a server's (COPL-224)
  "agents": [{                    // one per configured agent, in daemon.toml's order
    "slot": 0,                    // which of the daemon's agents, stable across reloads
    "configured": "me/dev",       // the handle as daemon.toml has it
    "handle": "me/dev",           // as the server says, once it has
    "user_id": "u-1",             // null until the server has said
    "url": "https://copland.example",
    "state": "running",           // starting, watching, running or stopped
    "live": "connected",          // the live socket: connecting, connected or reconnecting
    "last_poll": "2026-10-04T23:21:41Z",
    "unread": 4,                  // unread inbox items at the last poll
    "waiting": ["T-2"],           // tasks with unread items no run is on, oldest first
    "messages": 1,                // messages waiting for the next message run
    "retiring": false,            // a reload changed or removed it; it winds down after its runs
    "unavailable_since": null,    // Copland not answering since then: nothing starts meanwhile
    "held": false,                // held on this machine (the socket's hold): nothing starts until released
    "out_of_usage_until": null,   // its runtime's account is out of usage until then (COPL-195), RFC 3339; null when it isn't
    "account": "claude-code (b…@…)", // its runtime account (COPL-232), masked: a short hash, or the config's account
    "waiting_for_slot": null,     // the account whose max_runs_per_account holds its work back, while it does
    "runs": [{                    // every run going, oldest first
      "run": "aaaa",              // short id
      "task": "T-1",              // null for a run on messages
      "kind": "task",             // task or messages
      "since": "2026-10-04T23:20:41Z",
      "worktree": "/code/repo/T-1" // null in the agent's workdir, or before it is made
    }],
    "repos": [{                   // each board repo checked from here (COPL-178); [] without a code_command
      "repo": "o/r",              // owner/name, or a plain remote without its scheme
      "clone": true,
      "push": false,              // false: its coding tasks are left in todo for a machine that can
      "detail": "clones, but can't push: Permission to o/r.git denied to me." // null when both work
    }],
    "missing": "bwrap not found on PATH: coding runs can't start", // what this machine lacks; its runs wait
    "needs": [{                   // what needs the owner
      "why": "missing",           // stopped (not watching), missing (runs can't start), repo (one it can't push to) or failed (the last run)
      "says": "bwrap not found on PATH: coding runs can't start"
    }],
    "last_error": "…",            // the last thing that went wrong, cleared by the next good poll
    "last_run": {
      "run": "cccc", "task": "T-9", "kind": "task",
      "outcome": "failed",        // completed, failed, cancelled, or "skipped (…): …" when the claim was refused
      "failed": true,             // its runtime died or never started, or the run couldn't get going
      "skipped": false,           // nothing launched; outcome says why
      "how": "exit 1 after 3.8s", // how its runtime ended, once launched
      "hint": null,               // the plain word for a runtime that died at once with nothing to say
      "log": "/home/me/.local/state/copland/runs/….log",
      "ended": "2026-10-04T23:21:11Z"
    }
  }]
}
```

`DaemonState` carries what this needs: each run's worktree (`ActiveRun::worktree`, set once the workspace is made) and what the machine lacks (`AgentState::missing`, also said in `last_error` after a good poll, which is where the box draws it).

### The status socket

`copland-daemon` serves this on a Unix socket next to its config's lock (COPL-184): `$XDG_RUNTIME_DIR/copland/daemon-<hash>.sock`, the same hash as the lock's, so two daemons on two configs never share one (`Lock::socket`, `core/src/socket.rs`). It is made mode 0600 in a 0700 directory, and a client whose uid (`SO_PEERCRED` on Linux, `getpeereid` on macOS) isn't the daemon's is hung up on, so only you can read it or stop your runs. It is removed when the daemon ends. One left by a daemon that was killed is replaced at the next start; the lock is what keeps two daemons off one config, and whoever holds it owns the socket.

The protocol is newline-delimited JSON: one request per line, one answer per line, in order.

```jsonc
{"op":"status"}                          // → one Status, as above
{"op":"watch"}                           // → a Status now, and another on every change, until you hang up
{"op":"stop_run","slot":1,"run":"aaaa"}  // → {"ok":true}: stops that run as the box's ■ does
{"op":"hold","slot":1}                   // → {"ok":true}: holds that agent on this machine
{"op":"release","slot":1}                // → {"ok":true}: releases it
{"op":"reload"}                          // → {"ok":true,"reloaded":{"kept":[…],"started":[…],"rebound":[…],"stopped":[…]}}
```

Holding an agent (COPL-186, `Daemon::holder()`, `Holder::set`) is local and light: while it is held, its loop starts no run and claims nothing, the same as while Copland is unavailable, and runs already going finish as they would. It still polls and keeps its live socket, so its status stays current (`held` is true, `waiting` lists what waits, and the text says "held on this machine"). Releasing it polls at once, so the work waiting starts within one poll. A reload keeps a slot's hold; a restart of the daemon forgets it, since it is never written to `daemon.toml`. It is not Copland's pause: that is the pause button on the agent's settings page (`PATCH /api/agents/:id`), a kill switch that stops the agent's tokens everywhere, which a person sets and the daemon only ever reads. Holding or releasing an agent that is already so answers `{"ok":true}` too. Releasing one also ends a hold for being out of usage (above): whoever releases it says to try now.

`reload` (COPL-197) has the daemon read its config file again, the one it was started with, and run what it says now, as the box's agents screen does after saving (`Daemon::reload`, see "The agents screen"): new agents start, removed ones stop and changed ones start again with what changed, each after its runs. `reloaded` lists the agents by handle as `daemon.toml` has them: `kept` as they were, `started`, `rebound` (changed) and `stopped`. A file that doesn't load, or a reload the daemon refuses (it is stopping, an agent's `url` isn't one), answers `{"error":"…"}` and changes nothing. The answer comes once the reload is done, which is at once: winding down after a run happens afterwards, and shows in the status (`retiring`). The headless daemon does the same on SIGHUP, logging what changed.

`slot` and `run` are an agent's `slot` and one of its `runs[].run` in the status. Anything that can't be done (an unknown op, a line that isn't JSON, a slot with no agent, a run that isn't going) answers `{"error":"…"}` and keeps the connection; an answer with `error` is never a status. While watching, requests can still be sent on the same connection, and their answers come in between the snapshots. A request line over 64 KiB is answered with an error and hung up on. Changes in quick succession can come as one snapshot: each is the state as it is then, never a diff. Try it with `socat - UNIX-CONNECT:$XDG_RUNTIME_DIR/copland/daemon-<hash>.sock` and a request.

### `copland-daemon status`

The socket from a terminal or a script (COPL-185, `core/src/client.rs`). It finds the socket for the config as the daemon does, so `--config` picks the daemon to ask, the default config's when left out.

```sh
copland-daemon status                  # what it is doing, as text (Status::render)
copland-daemon status --json           # one Status as above, on one line
copland-daemon status --watch          # the text again on every change it shows, until interrupted
copland-daemon status --watch --json   # one Status per line on every change, until interrupted
copland-daemon status --config ~/work.toml
```

`--watch` clears the screen before each snapshot on a terminal, and separates them with a `---` line otherwise. `--json` writes each line as the socket sends it, so fields a newer daemon adds come through.

`copland-daemon hold <handle>` and `copland-daemon release <handle>` (COPL-186) hold an agent on this machine and let it go, through the socket's `hold` and `release` (above). The handle is the agent's, as Copland says it or as `daemon.toml` has it, with or without the @; the line they print says what they did, and an agent the daemon doesn't run is an error naming the ones it does.

`copland-daemon reload` (COPL-197) is the socket's `reload`: after editing `daemon.toml`, it has the running daemon read it again and prints what changed (`started: @me/new`, `stopped (after its runs): @me/old`, `nothing changed`). A file that doesn't load is an error (exit 1) naming what is wrong, and the daemon goes on as it was. The service's unit runs it as its `ExecReload`, so `systemctl --user reload copland-daemon` does the same.

Exit codes, for all of them: 0 when shown or done (or a watch whose reader went away); 3 when no daemon is running the config (no socket, or one a killed daemon left), with a line on stderr saying how to start one, and the same when the daemon stops during `--watch`; 1 for anything else, including a daemon from before the socket holding the config's lock.

### Watching it from another program

A program that lives alongside the daemon (the tray, COPL-172) uses `Watcher` (`core/src/watcher.rs`, COPL-200) rather than the terminal's client. `Watcher::start(config, runtime_dir)` finds the socket as `status` does, sends `watch` and keeps a `tokio::sync::watch::Receiver<Connection>` (`subscribe`) up to date: `Connecting` until the first try says something, `Connected(Status)` with the latest snapshot, `NotRunning` when no daemon serves the socket, a dead one's is left behind, it hangs up or it is stopping, and `Unreadable(why)` when what answers can't be read (a `version` other than 1, an answer that isn't a status, a socket it can't connect to), so nothing of it is drawn. Fields it doesn't know are ignored. When the daemon goes away it tries again every second and picks up one started later by itself; receivers are woken only when the value changes. `stop_run(slot, run)`, `hold(slot)`, `release(slot)` and `reload()` (COPL-197, answering what changed as `Reloaded`) each send their request on a connection of their own, which keeps the answer apart from the snapshots, and answer `Err` with the socket's `error` text, or with no daemon serving the socket, or after five seconds without an answer. Dropping the watcher stops it.

### `copland-tray`

The daemon in your bar's tray (COPL-198, `daemon/tray`): a StatusNotifierItem over D-Bus, so it shows in waybar's tray, KDE's, and GNOME's with the AppIndicator extension. It is a small binary of its own, not the box, and needs nothing GPUI does. It watches the status socket of the daemon running a config (`--config`, the default config's when left out, as `copland-daemon status` finds it), and starts one only when asked from its menu: with no socket, when the daemon goes away and while it is stopping, it shows *not running*, and `Watcher` (above) picks up a daemon started later by itself.

```sh
copland-tray                       # the daemon running the default config
copland-tray --config ~/work.toml
```

Its icon is one of the four in `release/tray` (see "Cutting a release"): `needs` when any agent has something in `needs`, else `working` when any has a run going, else `idle` (held alone is idle), and `stopped` while no daemon is running. Its tooltip has a line per agent, the name part of its handle with what it is doing (`dev · working on COPL-166`, the task of its oldest run, `and 1 more` when it has others), `held` when it is held, `out of usage until 17:10 UTC` while its runtime's account is (COPL-195; not a need, so the icon stays as it was), and the first thing it needs. Its menu, on a left or right click, starts with Open the box, then has for each agent Hold or Release it on this machine (`Watcher::hold` and `release`, by slot) and Stop for each run going (`Watcher::stop_run`), then how it ends, which depends on the daemon (COPL-224). A workstation's daemon, started by hand, goes with the tray (COPL-225), so its menu has one way out: Quit Copland stops the daemon as `copland-daemon stop` does (`service::stop_daemon`: the service through `systemctl --user stop` or `launchctl bootout`, else SIGTERM to the daemon holding the config's lock), so runtimes stop, runs finish as interrupted and their tasks go back to todo, and then the tray quits. With a run going it is a submenu that says so first (`Quit Copland: 1 run on COPL-166 will go back to todo`, or each run and how many), and its one item quits. Nothing quits the tray alone. The tray going any other way (`systemctl --user stop copland-tray`, a crash it doesn't come back from, the session ending) takes the daemon with it too, and this is the daemon's doing, so it holds whatever started either: a daemon that doesn't start at login watches the config's tray lock every second (`lock::tray_gone`), and once a tray has shown it and none has held the lock for 30 seconds (`lock::TRAY_GRACE`, longer than the tray's unit's `RestartSec=10`), it stops as on SIGTERM. A tray that restarts within that, or a second one that takes over, keeps it; a daemon no tray has shown (the box's, or one on a machine without the tray) never stops this way. Taking a lock is tried three times 20 ms apart before it counts as held, so the daemon's look at the tray's lock never turns a tray starting in that instant away. A server's daemon, the service started at login (the status's `autostart`, which the daemon reads at start from `systemctl --user show`, enabled with itself as `MainPID`, or on macOS the plist's `RunAtLoad` with launchd having started it), is meant to outlive the tray, so there is only Quit tray (daemon keeps running). With no daemon running, the menu offers Start Copland, which runs `copland-daemon start` on the tray's config (the service, else a daemon for the session) and then Quit tray. One tray shows a config: it holds the config's tray lock (`lock::tray_path_for`, beside the daemon's), a second one started on it (its autostart entry and its unit both) leaves at once, and `copland-daemon stop` stops the tray by its unit or, failing that, by SIGTERM to the lock's holder. What the daemon refuses, why its answer can't be read (`Unreadable`), or that a daemon from before the socket holds the config's lock, is the tooltip's last line and the menu's first, disabled, until the next request goes through or the connection changes.

Open the box (COPL-201, `open.rs`) starts `copland-box --config <the tray's config>`: the one beside the tray (they ship together), else the first on PATH. It is detached the way a launcher would start it, in a process group of its own with its output appended to `$XDG_STATE_HOME/copland/box.log`, so quitting the tray leaves it open. The box is a client of the daemon (COPL-204), so it is the same whether a daemon is running or not; with none, the box offers to start one. Nothing says whether a box is already open on a config, so each click opens another. A box that exits within two seconds (no display, a library missing) is said where the daemon's errors are, naming the log, until the next thing the tray sees.

To start it with your session, there is an XDG autostart entry, `$XDG_CONFIG_HOME/autostart/copland-tray.desktop` (`~/.config/autostart`), running `copland-tray` as found on PATH, else the one beside whatever writes it, with `--config` when the config isn't the default. A PATH directory that won't last (see Server mode's list) is passed over, and a tray beside the writer in such a place gets no entry: the switch, or setup, says why and how to install it to `~/.local/bin` (COPL-219). The box's menu writes or removes it (settings › tray at login), and `copland-daemon --setup` offers it (Setting it up on a terminal). Under Nix neither writes one: the module's `tray.enable` runs the tray as a user service, the menu's switch reads `nix` and says so, and setup doesn't ask. The writer is core's (`core/src/autostart.rs`), the same that writes the box's own entry. GNOME shows the tray only with the AppIndicator extension; KDE Plasma, waybar and most other bars have a StatusNotifierItem tray built in. A server needs none of it.

`view.rs` turns a status into the icon, tooltip and menu as plain values, and `follow.rs` keeps what the tray shows from the `Watcher` and passes the menu's requests to it; both are platform-neutral, for the macOS item (COPL-202). `sni.rs` draws them with `ksni` (pure Rust, no GTK), on its async-io runtime rather than its default tokio, which keeps zbus at the box's version and features. It is Linux only for now: elsewhere the binary says so and exits 1.

## Building

It's a Cargo workspace: `core` is a library with the loop, and `cli` is the `copland-daemon` binary. `tray` is `copland-tray` (above), and `box` is `copland-box`, a GPUI window on the daemon (below). `Daemon::subscribe()` hands out the daemon's state (each agent's phase, last poll, unread count, waiting tasks, messages waiting for a run, last run) as a `tokio::sync::watch` receiver, which the status socket serves as a `Status` (see "Status"), and the box draws from there. `Daemon::reload(config)` changes the agents it runs in place (see "The agents screen"). It needs the daemon itself, so the status socket's `reload` (which the box's agents screen sends) hands a `Reload` to whoever owns it (`Daemon::reloads`), the headless loop, which also answers SIGHUP. The workspace's `default-members` are `core`, `cli` and `tray`, so plain `cargo` here builds and checks the headless daemon and the tray, with no GPUI anywhere in their graph.

```sh
cd daemon
cargo build --release      # target/release/copland-daemon and copland-tray
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

TLS is rustls with ring, so there is no OpenSSL and no cmake to find; on NixOS plain `cargo` builds it. `--headless` is accepted and is the only mode `copland-daemon` has; the window is the separate `copland-box` binary.

## The box

`copland-box` is a window on the daemon (COPL-33, a client of it since COPL-204). It runs no agents: `copland-daemon` does (usually as a user service, `copland-daemon --install-service`), and the box watches the daemon running its config through that daemon's status socket (`Watcher`, see "Watching it from another program"), stops a run and reloads `daemon.toml` through it, and draws your agents' work as the wired scene, the same one as the web's /wired pane (`src/features/wired/scene.ts` and `WiredPane.tsx`, designed in `docs/research/wired-prototype.html`): four poles on one ground line, todo, doing, blocked half a span on and done a span on, each with its list underneath. Tickets wait on the wire into doing, a run's sits at the doing pole while current runs along its wire, blocked ones take the short span and wait by the blocked pole, and done ones ride the long span that sags under blocked and fade off the edge. The geometry, the default tuning and the per-frame update are a port of the web scene, kept close enough to read side by side; when the web scene's geometry changes, the box's has to follow by hand, and its tests fail until it does (see "Building the box"). All of it is in `box/src/scene.rs`: the layout is the constants and `Layout`/`build_wires` at the top, and `view.rs` places the lists by the web pane's rule (`budgets`).

The scene is drawn on a 170×22 grid at 3 screen pixels per cell, rounded to whole device pixels on scaled outputs. It is composited in software the way the web's canvas is, then painted as one GPUI quad per horizontal run of same-coloured cells, a few hundred quads. The lists and the status line are text in JetBrains Mono when the system has it, else fontconfig's monospace, else DejaVu Sans Mono. No font is bundled. Each list shows the longest form of its lines that all of them fit, as the web does: doing drops its run's host (the box's alone, see The agents screen), then the timer, then the agent; blocked the agent, then the mark. At the box's size the full forms fit for ordinary keys and names.

The window is 548×196, or 548×26 in compact mode (below). Its minimum is the compact size, so it can shrink to that when compact is switched on; Wayland has no way to ask for a fixed size, and GPUI 0.2.2 sends only the minimum anyway. When the compositor gives it more anyway (tiling, a rule, a resize), the box draws at the largest whole multiple of its natural size that fits, 6 pixels per cell at twice the size and so on, with the text and gaps scaled to match, and centres the scene in the space. The title and status lines run the full width. Smaller than 548×196 it stays at its natural size and is cut off.

It draws only when something changes: 30 frames a second while a ticket travels or fades (not every display frame, so a high-refresh screen doesn't mean 144 renders a second), 15 while a run's current flows (`FPS` in `scene.rs`, the web scene's cap), 12 while the wires only sway (they move about a cell a second, so it looks the same and costs less), once a second while a run's timer shows with `motion = false`, and otherwise when the daemon's state or the owner's feed changes (and every 30 seconds for the done list's slow fade). GPUI has no reduced-motion setting to follow, so `motion = false` in `daemon.toml` is the switch.

Compact (below) redraws for the scene once a second at most: only the status line shows, and it changes only as a run's timer ticks or a ticket arrives, so the scene catches up on the frames in between (`Scene::catch_up`) instead of being drawn at 12 to 30 a second for nobody. A window that can't be seen draws nothing at all, and the box does nothing to make that so: GPUI draws on Wayland's frame callbacks, Hyprland sends none to a window on another workspace or a hidden special one, so `render` isn't called and no redraw is scheduled. The daemon, the feed and notifications carry on, and the first frame after it shows again picks up from there. Measured on Hyprland 0.56 with the demo (COPL-129), as a share of one core over 30 seconds: the whole box visible 20% (24 frames a second), on another workspace or a hidden special workspace 0% (no frames), compact 29% (25 frames a second) before and 1% (one) after.

What it shows, live, with `owner_token_file`:

- The box reads `GET /api/wired` with your token when your live socket (the same `/api/live`, with the same token) says a board, your boards, your agents or people changed, at most once every five seconds (COPL-209, `SPACING`): the first wake after a quiet spell waits 300 ms for the rest of its burst, one inside the window waits for its end, and what came in meanwhile, inbox, boards and settings too, is one read. Its socket dropping reads everything again, through the same window, so a network that keeps dropping is a read a window. A board change that names its tasks (COPL-151) is skipped when none of them is on /wired and none of your agents is, or was, assigned to them, since every task /wired shows is one of your agents' (`Due::of` in `box/src/feed.rs`); one that doesn't say still reads it. One that does reads just those tasks (COPL-211): `GET /api/wired?tasks=` for the ones it shows, or all of them when one of your agents is on them, at most 50, sorted onto the last whole read the way the server sorts each pole, by the stage and rank each task carries (`merge`). The whole is read instead when there are more, when that read fails (an older server), and while done is past its limit (its count above what it lists) and a task it didn't show turns up or a done one leaves, since only the whole read knows the ones past the limit. It also reads it two seconds after any of its runs starts or ends, and on a clock: every two minutes while the socket is up and every 15 seconds while it's down (a claim that lapses sends nothing, so the clock still matters). The status line ends in a faint `•` while every socket on the box (each agent's and yours) is up, and `◦ polling` while one is down. It is the same data as the web pane, so todo, doing (live claims with their timers, then active tasks no run holds, dimmer and without timer or current), blocked, and done in the last 24 hours with the count in the status line. This runs on the box's Tokio runtime (`box/src/feed.rs`), only while the box is open, and is handed to the window as a `watch` value, like the daemon's status.
- The daemon's own runs go over it: a run it has just started shows in doing at once, before the next read says so, and the two are matched by task key.
- When the data changes, each ticket that changed pole travels the wires to its new one, diffed by key; one nothing lists any more fades. The first read is placed as it is, without travel.
- Clicking a ticket opens the task in the browser, `<url>/b/<BOARD>?task=<KEY>` (its board with the task open), the board key being the task key's prefix.
- An agent's token given as `owner_token_file` is refused (the route is a person's own) and the box says so in the status line and stops reading; so does any other refusal. A failed read (the server down) keeps the last picture and says why.

Without `owner_token_file` it draws what the daemon alone knows, and the status line says to add the key: todo is the tasks with unread items for an agent (`AgentState::waiting`, published on every poll), doing is each agent's current run, and done and blocked stay empty. A task the daemon has already run stays in todo there while its items are unread, because that is what the inbox says. While no daemon is running its config, the scene draws no agents and the status line says so and offers to start one (COPL-205, `box/src/offer.rs`), with the box's keys and clicks like everything else: `i` installs the service (core's `service::install` with the `copland-daemon` shipped beside the box, `service::daemon_binary`), which starts it now but not at login (COPL-223: the panel says to start it again here, with `copland-daemon start` or its launcher); `s` instead, when `service::installed` finds one that is stopped, starts it; under Nix (the box in the store) there is no `i`, and `m` shows the home-manager module to add (`services.copland` with `tray.enable`, and `configFile` for a config that isn't the default) in the panel, where `c` copies it with the flake input and the import; `r` runs one for this session only (`service::spawn_session`: detached, so it outlives the window but not the login, logging to `$XDG_STATE_HOME/copland/daemon.log`). A panel under the poles says what came of it: the unit or plist written, where its log is, install's notes (lingering off so it stops at logout, another daemon already on the config), or what failed, in words; Enter dismisses it. A daemon started meanwhile, by the box or anything else, is picked up within a second, by itself.

A box from 0.4.x ran the agents itself, so closing it stopped them. The first time this box starts on a config with no service installed, it says, once, in a panel, that it no longer runs the agents itself and that the daemon now runs as a service, and offers the install (`i`), a session daemon (`r`) or not now (`n` or Esc). Under Nix it shows the module's panel (above) instead. Whatever the answer, it is kept in `$XDG_STATE_HOME/copland/box.toml` (`service_offered = true`), so it isn't asked again; it is a file of the box's own rather than a key in `daemon.toml`, since the service is the machine's and the daemon would refuse a key it doesn't know. The plain offer in the status line stays whenever no daemon runs. With no config it sets itself up (below); with one it can't use (no agents, a refused key) it shows the empty scene and "nothing on the wire" with the reason. `--demo` drives it with the prototype's simulation instead: no config, no server, nothing launched. In the demo `n` adds an item, `a` answers a blocked one and `f` finishes a run; `q` or Esc quits anywhere.

### Setting it up

A box started without a config sets itself up in its window instead (COPL-47); `copland-box --setup` does the same over an existing one, which is kept as `daemon.toml.bak` (or `.bak.2`, …). A config that is there but broken is not replaced by itself: the status line says why and points at `--setup`. `copland-daemon` without a config says to run `copland-daemon --setup`, the same setup on a terminal (see Setting it up on a terminal). Everything setup does but draw (reading the address, saving the tokens, finding the runtimes, writing the config) is in `core` (`core/src/setup.rs`, `core/src/runtime.rs`, COPL-174), with no GPUI in it; the box's `wizard.rs` drives it.

1. **Address.** Type your Copland's address; `https://` is added when there's no scheme, and anything after the host is dropped. `--url <address>` fills it in. Enter connects, ctrl+v pastes, Esc quits. It's a one-line field of the box's own (`setup::LineInput`), since GPUI 0.2.2 has no text input.
2. **Approve.** The box asks `POST /api/device/start` for a code, shows it large, and opens `/device?code=…` in your browser once (`o` opens it again). It polls `POST /api/device/poll` every `interval` seconds, slower when asked to (`slow_down`). Denied or expired says so; `r` tries again, `b` goes back to the address.
3. **Runtimes.** Once approved, the tokens are written at once, since the server hands them over only once: `me.token` (yours, read-only) and `<agent>.token` per agent, beside the config, the directory 0700 and the files 0600, plus a note `daemon.toml.setup` of what still needs saying. A box closed now picks up here next time. It looks on PATH for `claude` and `codex` and reads their `--version` (three seconds at most). Every agent gets the first found, Claude Code before Codex, working in `~/agents/<name>`. ↑↓ picks an agent, space changes its runtime. With none found it says what to install; `r` looks again.
4. **Save.** Enter writes `daemon.toml` and makes the working directories.
5. **Check.** The preflight (see Checking a machine) runs on the config just written, through setup's own Tokio runtime, and lists `✓`/`!`/`✗` per check, three at a time (↑↓ moves), with the selected one's fix under them. `f` runs a fix that only makes a directory (code_dir) and checks again; a fix that logs in or asks for a git identity wants a terminal, so `c` copies its commands to paste in one (or `copland-box --check --fix` and `copland-daemon --check --fix` offer them all), and `r` checks again. Enter goes to the live view in the same window, whatever the checks say (a box that does no code work needs no GitHub login), and starts the daemon on the new config (COPL-205): it installs the service, or, when one is installed already, starts it again (`service::restart`) so it reads the new config, and says what it did as the offer above does. Under Nix with no service it installs nothing and shows the module's panel instead. The view picks the daemon up once it answers; if starting it failed, the status line's offer is there to try again or run one for the session. The last line says to connect your own Claude Code or claude.ai to `<url>/mcp` and pick "you" when it asks who, so it acts as you and not as one of the agents. The config is written by now, so a box closed here starts on it next time without setup.

The commands come from `core/src/runtime.rs`, two templates per runtime, and every agent gets both, with no narrower preset to pick (COPL-160): an agent is there to do work. `command` is the narrow one above, Copland's MCP tools and nothing else, because it runs outside any sandbox; it is for runs with nothing to code, messages and tasks on boards without a repo. `code_command` is what runs on a board with a repo, in the task's own worktree inside the sandbox, with the runtime's own tools, and with it `writable` and `runtime` (see Coding tasks for Claude Code's, which is the example there). The written config says which is which. Codex has no flag for an MCP config file, so its command is a small `sh` that reads the run's secret out of `{mcp_config}` into `COPLAND_RUN_SECRET`, and runs `codex exec --ephemeral --skip-git-repo-check --ignore-user-config` with a read-only permission profile and Copland as an HTTP MCP server reading its bearer token from that variable, kept out of Codex's own shell. Whatever follows its arguments goes on to `codex exec`, so as a `code_command`, which setup writes it as too, the daemon's sandbox policy replaces the read-only profile (see Coding tasks). It has been run against Copland (COPL-143).

### The agents screen

The menu's agents panel (`a` in the live view goes straight to it) is the agents screen, in the same window, the poles staying behind it as they do for setup (COPL-55). It lists every agent you have in Copland, from the `agents` that `/api/wired` already sends with your read-only token (paused ones too), so without `owner_token_file` it lists only what this machine runs. Each agent is one of two kinds:

- **Runs here**: its name, runtime (Claude Code or Codex, or "(own)" when its `command` or `code_command` isn't setup's template for one, a widened one say; `writable` and `runtime` don't count, so a path added there by hand keeps the name), working folder, and what it is doing: watching, a task it has a run on, an error (a program its runs need that isn't on PATH among them), or "changes after this run". After a run that went wrong it says so in red until the next run: "× COPL-132 exit 1 after 3.8s" (COPL-136). The line under the selected agent then says which run it was, or, for a runtime that died within ten seconds having written nothing, "claude exited at once with no output: check the runtime outside the box", since that is almost always the runtime's setup and not the task. `o`, or a click on that line, opens the run's log. Space (or ← →) cycles the runtime through those found on PATH, marked as a change; Enter saves the changes. A config an older setup wrote has the template's `command` and no `code_command`, so it codes nowhere: it is named by its runtime, and the line under it says so and that choosing the same runtime again adds one. `x` twice stops running it here.
- **Not on this machine**: Enter asks Copland for that agent's token with a device login that names it (`agents` on `POST /api/device/start`), so `/device` ticks that agent alone; the box shows the code and opens the page, as setup does. Once approved, it writes `<name>.token` beside the config (another name if that file exists) and an `[[agent]]` table with the first runtime found, working in `~/agents/<name>`. Because the request names agents, the approval makes only their tokens: the box already has the read-only one for you.

`m` messages the selected agent, either kind (COPL-109). It opens one line under the name; Enter sends it with `POST /api/messages` as you, Esc goes back, and ctrl+v pastes. A message holds at most 1000 characters, and the line counts them. When the agent has a run going here, the line says the message waits for its next run, and so does the word after sending: nothing reaches a runtime that is already going (see Messages). Stopping a run and pausing an agent are not messages: `s` on the live view and the pause in Copland. Sending needs your write token, so the first `m` asks for it, with `write: true` on `POST /api/device/start` and no agents: `/device` then says it is a read and write token for you and lists no agents, and approving makes that one token ("<host> box, messages" in settings › access) and nothing else. Once it is saved, the line opens. Without `owner_token_file` there is nothing to ask with, and `m` closes the menu as it does elsewhere.

Each agent's name is followed by where it runs (COPL-183), "dev · laptop", from the `hosts` that `/api/wired` sends with each agent: the hosts it is live on now (its daemon's live socket names its host), else in fainter text the one it last reported from, else, for one that runs here, this machine. One live on two hosts at once, and not paused, gets the web app's warning under the list in yellow ("dev Live on laptop and server at once: usually a forgotten daemon. Stop the one you don't mean to run.", `twoHostsWarning` in `src/domain/hosts.ts`, whose wording the box's test reads), and the live view's status line ends in "dev live on laptop and server at once" while it lasts, unless the feed has an error to say. A run's host shows in the doing list, "COPL-12 dev · laptop 3m10": `/api/wired` names it for each live claim (the host its launcher gave `POST /api/runs`), and the daemon's own runs are on this machine. It is the first thing a narrow list drops.

↑↓ picks an agent, Esc closes the menu, and changes not saved are dropped. Paused agents say so.

Saving edits `daemon.toml` in place (`box/src/edit.rs`): only the changed agent's table, and in it only `client`, `command`, `code_command`, `writable`, `runtime` and the untested-template note, replaced together where `command` was so no other runtime's `code_command` is left behind, so comments and hand edits elsewhere stay. The file is checked the way the daemon reads it before anything is written, the old one is kept as `daemon.toml.bak` (or `.bak.2`, …, never over an older backup), and the new one is written whole with mode 0600. Stopping an agent here removes its table and leaves its token file, so the backup still works; the token stays valid until you revoke it in settings › agents. The last agent can't be stopped here (a config without one isn't a config); `--setup` starts over instead.

Then the box sends the daemon's socket `reload` (`Watcher::reload`, COPL-197), and the line says what was saved, or the daemon's error, for a file it won't load, say (nothing changed then), or that no daemon is running it. The daemon takes the new config without a restart (`Daemon::reload`, `core/src/daemon.rs`, the diff in `core/src/reload.rs`). An agent is the same agent across the two when its instance and handle are; one whose command, code command, writable paths, runtime, workdir, client, token, `max_runs` or `account` changed is rebound, one that's gone is stopped, one that's new is started, and the rest are left alone (all are rebound when `poll_interval` or `code_dir` changed; a new `max_runs_per_account` rebinds none and applies at each loop's next poll). Each agent's loop runs under a supervising task that holds its binding. A rebind or a stop bumps the binding's generation, which the loop looks at only between polls and before starting a run; it is never passed to a runtime. So an idle loop ends at once, and a loop in a run lets the run finish, claim, keepalives, `finish_run` and all, under its old binding, then ends; only then does the supervisor start the agent again with the new one (or drop it). An agent never has two loops, so never two runs. The wake guard's memory goes from the old loop to the new, so a rebind doesn't relaunch on items already handled. If a reload comes between the check and a launch, that one run still uses the old binding; the next one uses the new.

### The menu

≡ at the right of the title bar, or `m`, opens the menu (COPL-65): small panels under the poles, one at a time, their names across the title bar. Click a name or press its number (1 to 6) to switch, Esc or `m` closes it. Everything in a panel works with the keyboard and the mouse alike: clicking a line does what pressing its key would, and so does clicking a key in the status line. `box/src/menu.rs`.

- **needs you**: what the bell counts (below), each line opening its task (a message about no task opens Copland, where your inbox is). `r` marks a mention or a message read, with your write token (`POST /api/inbox/read`; without the token it says how to get one).
- **agents**: the agents screen above.
- **boards**: which boards' tickets the scene shows, from `GET /api/boards` with your token. Space shows or hides one, `a` shows them all again. It is display only: the agents still wake for anything on any board, and the bell still counts blocks on hidden ones. With a filter on, done's count is what is left of the listed ones.
- **settings**: the theme (the seven, then "copland", yours there), motion, notifications, start at login, tray at login and compact. Space or ← → changes the selected one, and it applies at once.
- **session**: who the box is signed in as, on which Copland, and the tokens it holds. `x` twice signs out (below).
- **about**: this version, and whether a newer box is out. It asks GitHub's releases API for `box-v*` tags on berker-z/copland once, without a credential, keeps the answer in `$XDG_STATE_HOME/copland/release.toml` for twelve hours, and says so plainly when it can't ask. `r` asks again, `o` opens the releases.

Settings and boards are written to `daemon.toml` when the menu closes, once for everything changed, through the same editor as the agents screen (`edit::set_key`): an existing key is replaced where it is, a new one goes after the last top-level key, comments stay, and the old file is kept as `daemon.toml.bak` (`.bak.2`, …). Start at login is a file of its own, written or removed as it is switched: `$XDG_CONFIG_HOME/autostart/copland-box.desktop`, running `copland-box` as found on PATH (a Nix profile's link, which follows upgrades, not the store path behind it), else this binary, with a word in the panel when that is a store path. A box in a place that won't last (a tarball's versioned directory, a download or temporary one, a build tree; see Server mode) writes no entry, and the panel says how to install it to `~/.local/bin` (COPL-219). `--config` goes into it when the box was started with one that isn't the default. Tray at login is the same for `copland-tray.desktop`, running the `copland-tray` on PATH, else the one beside the box (see `copland-tray` above); under Nix it reads `nix`, writes nothing, and points at `services.copland.tray.enable`. Both are written by `core/src/autostart.rs`.

Compact shows the status line alone in a 548×26 window, with the bell, ≡ and × at its end; it drags like the title bar. Opening the menu grows the window back for as long as it is open. The box resizes itself (`Window::resize`), and on Hyprland asks for the size over IPC as well (`hyprland::resize`, floating it where it is, without centring), since a rule's `size` would otherwise win. Started compact, it is sized that way even when a rule floats it.

### What needs you

The bell in the title bar (drawn in pixels like the scene) counts what needs you (COPL-64): your agents' tasks in a blocked stage, from `/api/wired`, and unread items in your own inbox that @mention you or are a message from one of your agents (COPL-109, one line each, its text shown), from `GET /api/inbox?unread=true` with your read-only token, read again when your live socket says `inbox`. It is faint at nothing and yellow with the count otherwise. It is a subset of your web inbox, not a copy of it: only mentions, your agents' messages and their blocks, so its count is usually lower than the web's, while what both show is the same state. Opening a need's task on the web reads it: the web marks your unread items on a task read when you open it (messages aside), `inbox` goes out, and the bell drops it within a few seconds. Clicking it, or `b`, opens the needs-you panel.

A desktop notification fires once for each new one, quietly: no sound (the box plays none and asks the notification server not to with `suppress-sound`), nothing for routine moves, and more than three at once are one notification. Clicking it opens the task. On Linux it goes over D-Bus to `org.freedesktop.Notifications` with zbus, which GPUI already brings, so no crate was added. macOS has none yet (a TODO in `box/src/notify.rs`: it needs a signed app). What was said is kept in `$XDG_STATE_HOME/copland/notified.toml`, so a restart repeats nothing; a need that goes away (unblocked, read) is forgotten, so a task blocked again later is said again. The first time, with no such file, whatever is already there is remembered without a burst. The settings panel switches the notifications off (`notifications = false`); the bell counts either way.

### Stopping a run

A ticket in doing that this box is running gets a ■ in front of it. Click it, or press `s` (tab picks the next run when there are several), and the box asks "stop COPL-12's run?"; a second click or `s` within six seconds stops it, anything else keeps it. Stopping is the same as at shutdown, for that run alone: SIGTERM to the runtime's process group, SIGKILL ten seconds later, and the run finishes as cancelled. The wake guard remembers the task's items as after any run, so it isn't started again until something new comes. The box asks over the daemon's socket (`Watcher::stop_run`); what the daemon refuses (a run that ended meanwhile) is said in the status line. Underneath it is `Daemon::run_stopper()` (`RunStopper::stop(slot, run)`), which the agent's loop watches during a run, and which the socket's `stop_run` calls.

### Signing out

`x` twice on the session panel signs the box out: it revokes every token `daemon.toml` names (your write token too), each with itself through `DELETE /api/tokens/self` (the one token-management call a token may make, on itself only; see AGENTS.md), then deletes the token files, `daemon.toml` with its backups and setup note, and `notified.toml`, and starts setup in the same window with the address filled in. Before any of that it stops the daemon running the config (`service::stop_daemon`), so nothing runs on tokens about to go: the installed service is stopped (not removed, so it still starts at login if it did), and any other daemon still holding the config (a session one, or one on a terminal) gets SIGTERM, its runs ending as at any shutdown, and the box waits up to 20 seconds for it to let go. Setup's end starts the service again on the new config. A daemon it couldn't stop or a token it couldn't revoke (the server down, say) is named there, the token to revoke in settings › tokens. To switch accounts or add one, sign out and set up again; the box holds one at a time.

### Closing it, and its colours

Closing the window closes the box and nothing else: the daemon and its runs go on, and opening the box again draws them where they are. SIGINT and SIGTERM end the box the same way. Desktop notifications stop with it; the tray (COPL-172) is what notifies with the box closed. The title bar drags the window (GPUI's `start_window_move`).

The colours are Copland's seven themes, copied from `src/styles/themes.css` into `box/src/theme.rs`. They have to be kept in step by hand; a test reads the CSS and fails when they differ. Pick one with `theme = "nord"` at the top of `daemon.toml` (the headless daemon ignores the key) or `--theme` (for that run only), or from the menu. `theme = "copland"` follows the theme you chose in Copland: the box reads `GET /api/settings` with your read-only token (a person's own read, which an agent's token can't make) and again when your live socket says `settings` changed; until it has, and without `owner_token_file`, it is nord.

### Its log

Started from a launcher (Hyprland's `exec-once`, the desktop entry) the box's stderr goes nowhere, so it also logs to `$XDG_STATE_HOME/copland/box.log` (`~/.local/state/copland/box.log`, next to `runs/`), mode 0600, appending across starts (COPL-163). Each start writes a `copland-box version=…` line, and a panic goes in as well as to stderr. The file is capped at 1 MiB: past that it moves to `box.log.1`, replacing the one before, and a new one starts, so the two never hold more than 2 MiB. It still logs to stderr too, coloured when that is a terminal (the file never is). By default both get Copland's own lines at info and everything else (GPUI's locale, fonts and Vulkan setup, hyper) only at warn; `COPLAND_LOG` replaces that filter entirely, `COPLAND_LOG=debug` for everything (COPL-166). `copland-box --check` prints where the log is on its first line. When the file can't be opened (a read-only state dir), the box says so on stderr and carries on without it.

### Hyprland

Hyprland floats a window by itself when its minimum and maximum size are equal. The box would say so, but GPUI 0.2.2 sends only the minimum size on Wayland (`window_min_size`; `is_resizable` does nothing on Linux), so Hyprland tiles it. Until GPUI can, the box does it over Hyprland's IPC socket (`box/src/hyprland.rs`): once its window shows up in `j/clients` it floats it, sizes it to 548×196 and centres it, by its own pid, so another box or anything else is left alone. A window that is already floating when it appears is left as it is, because then a rule put it there. It tries the Lua dispatchers first (`hl.dsp.window.float` and friends, Hyprland 0.55 and later with `hyprland.lua`) and the old ones (`setfloating`, `resizewindowpixel`, `centerwindow`) when those are refused. The Lua ones were checked on Hyprland 0.56; the old ones weren't. You may see it tiled for a frame or two first.

Keeping it on top and on every workspace still takes a rule: Wayland has no way for a window to ask for that. `copland-box --hyprland-rule` prints one for the box's size, for `hyprland.lua` and for an older `hyprland.conf`, floating and pinned in the bottom-right corner with no border. For the Lua config it is:

```lua
hl.window_rule({
	match = { class = "^(copland-box)$" },
	float = true,
	pin = true,
	size = { 548, 196 },
	move = { "monitor_w-572", "monitor_h-244" },
	border_size = 0,
	rounding = 0,
	no_shadow = true,
})
```

The move puts it 24px from the right and 48px from the bottom. Use constants there, not `window_w`: the rule is evaluated against the size the window would have had tiled, which changes with whatever else is on the workspace. The Lua rule was checked on Hyprland 0.56; the `windowrulev2` lines weren't.

### Getting it

You don't have to compile it. Each `box-vX.Y.Z` tag gets a GitHub release, built by CI (`.github/workflows/box-release.yml`), with a `SHA256SUMS` file covering everything in it:

- **Linux x86_64 and aarch64:** `copland-box-<version>-linux-<arch>.tar.gz` has the three binaries (`copland-box`, `copland-daemon` and `copland-tray`), their launcher entries, the icon, the daemon's systemd user unit (Server mode), an `INSTALL` note and the licence, laid out like `~/.local`. Unpack it and `mkdir -p ~/.local && cp -r --remove-destination bin share ~/.local/` puts the binaries in `~/.local/bin` (the service, the tray at login and the box's start at login run them from there, and refuse to run them from the unpacked tarball, Server mode), `copland-box.desktop`, `copland-tray.desktop` and `copland-daemon.desktop` (the daemon's launcher, Server mode) in `~/.local/share/applications` and the icons under `~/.local/share/icons/hicolor`. It's built on Ubuntu 24.04, so it needs glibc 2.39 or newer (the release notes give the exact floor, read from the binaries). The window also needs a Vulkan driver, Wayland or X11, xkbcommon and fontconfig, which a desktop has anyway, and coding runs need bubblewrap (`bwrap`) on the PATH the box is started with. It isn't in the tarball: install your distribution's, the `bubblewrap` package on Arch, Debian, Ubuntu and Fedora alike (`pacman -S bubblewrap`, `apt install bubblewrap`, `dnf install bubblewrap`). Use that one and not a copy of your own: on Ubuntu 24.04 and later AppArmor lets only the distribution's `/usr/bin/bwrap` make the user namespaces it needs. The daemon says which it is when coding runs can't start (see "Coding tasks" above). On NixOS use the flake below instead: a plain binary won't find those libraries there.
- **macOS Apple Silicon:** `copland-box-<version>-macos-arm64.zip` is `Copland.app` (the box, with `copland-daemon` beside it in `Contents/MacOS`), and the `.tar.gz` next to it has the bare binaries, with the daemon's launchd agent as a template (Server mode). Neither is signed or notarized, so macOS refuses to open them at first: right-click the app, Open, and confirm, or `xattr -dr com.apple.quarantine Copland.app`. This build compiles and answers `--version` on CI and has never run on a real Mac. Started from Finder it gets Finder's short `PATH`, so give the runtimes in `daemon.toml` full paths. Coding runs need nothing installed: they are sandboxed with Seatbelt, which macOS has built in (`/usr/bin/sandbox-exec`, see "Coding runs" above); CI tries that sandbox on macOS 14, nobody has on a real Mac yet.
- **Nix:** `nix run github:berker-z/copland/box-vX.Y.Z?dir=daemon`, or the flake input below. The release workflow pushes both Linux systems' builds to the `copland` Cachix cache, so with the cache as a substituter (`cachix use copland`) Nix downloads the box instead of building GPUI. The cache's key is in `flake.nix`, so `--accept-flake-config` does the same without cachix.

Windows and Intel Macs get nothing yet.

### Installing it

`daemon/flake.nix` packages the three binaries, `copland-box`, `copland-daemon` and `copland-tray`, built from `Cargo.lock` with [crane](https://github.com/ipetkov/crane) (every crate comes from the lock, offline). Crane splits the build in two: `./daemon#deps` compiles every dependency, GPUI included, from `Cargo.toml` and `Cargo.lock` alone, and the package compiles our four crates on top of that (from the Rust sources, plus the tray's icons in `release/tray`, which it builds in). The dependencies are nearly all of the work and change only with the lock, so after the first build a change to our code rebuilds in a fraction of the time, and the finished package comes from the Cachix cache (see "Getting it"). The x86_64 deps derivation (about 600 MiB) is pushed too, so a new commit only compiles our crates even on a fresh machine; aarch64 pushes only its package. On the free Cachix plan (5 GiB for the whole account, least recently used paths evicted when full) that leaves room for other projects' caches. crane is pinned to a commit in `flake.nix` like nixpkgs, and builds with that nixpkgs. GPUI loads the Vulkan loader, Wayland, X11, xkbcommon and fontconfig at run time, which NixOS doesn't put on a library path, so the package adds them to the box's RPATH. Not `LD_LIBRARY_PATH` in a wrapper: that would leak into everything the box starts, the runtimes and your browser included. bubblewrap is pinned the same way: the build sets `COPLAND_BWRAP` to its store path, which both binaries start coding runs with instead of looking on PATH, so a box started from a desktop launcher runs coding tasks too, and nothing is added to the runtimes' environment. The package also has the daemon's systemd user unit, `share/systemd/user/copland-daemon.service` with its own store path in `ExecStart` (Server mode), and a desktop entry (`copland-box.desktop`, "Copland", named after the window's app id so docks match the two) and the Copland mark as its icon, the SVG plus PNGs from 32 to 256 pixels, and the tray's entry (`copland-tray.desktop`).

From a checkout:

```sh
nix run ./daemon                      # the box (same as ./daemon#box)
nix run ./daemon -- --demo            # arguments go after --
nix run ./daemon#daemon -- --setup    # set the headless daemon up on a terminal
nix run ./daemon#daemon -- --check    # the headless daemon
nix run ./daemon#tray                 # the daemon in your bar's tray
nix run ./daemon -- --check --fix     # check this machine, offer the fixes (no window)
nix build ./daemon                    # ./result/bin/copland-box, copland-daemon and copland-tray
nix profile install ./daemon          # on PATH for good, with the launcher entry
```

Without a checkout it's `nix run github:berker-z/copland?dir=daemon`, and so on. Nix only sees files git tracks, so a new file in `daemon/` needs at least `git add -N` before any of these find it.

On NixOS (or anywhere with home-manager), take it as a flake input and import its home-manager module, which installs the package and runs the daemon, and optionally the tray, as systemd user services:

```nix
# flake.nix
inputs.copland = {
  url = "github:berker-z/copland?dir=daemon";
  # Not `follows`: the dependencies are built against its own pinned nixpkgs,
  # which is what the Cachix cache has builds for. The module builds the
  # binaries against yours anyway (below).
};

# your home-manager configuration (or home-manager.users.<you> in NixOS)
imports = [ inputs.copland.homeManagerModules.default ];

services.copland = {
  enable = true;
  # On the daemon's PATH, ahead of your profiles: the runtimes daemon.toml
  # names, and what their runs use.
  runtimes = [ pkgs.claude-code pkgs.codex pkgs.git pkgs.gh ];
  tray.enable = true;
  # A server: start at login, and at boot with `loginctl enable-linger`.
  # Leave it out on a workstation, which starts it from its launcher.
  # autostart = true;
};
```

Add the `copland` Cachix cache as a substituter (`cachix use copland`, or `nix.settings.substituters` and `trusted-public-keys` with the key in `flake.nix`'s `nixConfig`), or the first switch compiles GPUI.

The module doesn't install the cached package as it is: it builds the binaries against your configuration's `pkgs` (`copland.lib.mkCopland pkgs`). The box loads your system's GPU driver from `/run/opengl-driver`, which your nixpkgs built, and a binary linked to the flake's older glibc can't load it once yours moves past it: the loader prints `GLIBC_2.44' not found (required by libLLVM…)`, finds no GPU, and the box panics with `Unable to init GPU context`. Mesa's AMD driver links LLVM and hits this first; Intel's doesn't link it and can keep working for a while. The compiled dependencies, GPUI among them, are still `deps` from Cachix, built with the same rustc and the same vendored sources, so a switch compiles only the crates whose build scripts read your libraries' pkg-config paths, and ours. `overlays.default` does the same for `pkgs.copland`. `nix run` and `packages.${system}` stay the pinned, fully cached build, which works as long as your drivers' glibc isn't newer than the flake's.

`nix flake update copland` takes the newest box; nothing else moves it, and each switch points the units at the package it installed, so an upgrade or a garbage collection never leaves them on an old build.

The module (`nix/hm-module.nix`, COPL-217) has seven options under `services.copland`:

- `enable`: puts the package in `home.packages` (with its launcher entries, the "Copland Daemon" one included) and the daemon in `systemd.user.services.copland-daemon`: `release/copland-daemon.service` (Server mode, above) with `${package}/bin/copland-daemon --headless` in ExecStart, the same reload, restart and `KillMode=mixed`. It starts at nothing: start it from the launcher, `copland-daemon start` or the box (COPL-223).
- `autostart`: `false` by default; `true` adds `WantedBy=default.target`, so it starts at login, and at boot with `loginctl enable-linger`. For a server or a headless machine.
- `package`: `copland.lib.mkCopland pkgs`, the package built against your nixpkgs (above), unless you give another.
- `runtimes`: packages whose `bin` leads the unit's `PATH`, followed by `~/.nix-profile/bin`, `/etc/profiles/per-user/$USER/bin`, the system's profile and `/usr/bin`, so a runtime home-manager or NixOS installs is found anyway; at start the daemon adds your login shell's `PATH` and `~/.local/bin` and the like after these ("Where runtimes are found", COPL-216), so one from npm is found too, but a declared one wins.
- `configFile`: `null`, the default, is `~/.config/copland/daemon.toml`; an absolute path (or `%h/…`) goes to the daemon and the tray as `--config`. Either way the file is yours, written by `copland-daemon --setup` or the box: it holds the agents' tokens, so it stays out of the Nix store. Set it up once (`copland-daemon --setup`) and `systemctl --user restart copland-daemon`; until then the service fails to start and retries every ten seconds.
- `tray.enable`: `copland-tray` as `systemd.user.services.copland-tray`, part of `graphical-session.target`, after the daemon; `copland-daemon start` (the launcher) starts it with the daemon.
- `tray.autostart`: `false` by default; `true` starts the tray with `graphical-session.target`.

`nix flake check ./daemon` evaluates the module in a minimal home configuration with a stub package (so it builds no GPUI), reads back the units it renders (no `WantedBy` by default, `default.target` and `graphical-session.target` with the two `autostart`s), and fails when the autostarting daemon's differs from `release/copland-daemon.service` in any `[Service]` or `[Install]` line; CI runs it (`.github/workflows/nix-ci.yml`) on a PR that changes the Nix files, `Cargo.toml`, that unit or the desktop entries. There is no NixOS VM test that starts the unit in a session yet.

To add only the package, `home.packages` (or `environment.systemPackages`) takes `inputs.copland.lib.mkCopland pkgs`, or `pkgs.copland` with `inputs.copland.overlays.default` in your overlays. The box itself isn't a service: start it from its launcher entry, or with the session as a unit of your own:

```nix
systemd.user.services.copland-box = {
  Unit = {
    Description = "Copland box";
    PartOf = [ "graphical-session.target" ];
    After = [ "graphical-session.target" ];
  };
  Service = {
    ExecStart = "${inputs.copland.lib.mkCopland pkgs}/bin/copland-box";
    Restart = "on-failure";
  };
  Install.WantedBy = [ "graphical-session.target" ];
};
```

The tray and the box need your compositor to start `graphical-session.target` and hand the user manager its environment (`WAYLAND_DISPLAY` above all), which Hyprland does under UWSM or with home-manager's `wayland.windowManager.hyprland.systemd.enable`. The runtimes in `daemon.toml` (`claude`, `codex`) are found as "Where runtimes are found" says: the unit's `PATH` (the module's `runtimes`, and NixOS's user manager's system and per-user profiles), then your login shell's, then `~/.local/bin` and the other usual places, so a `claude` from npm is found too; `copland-daemon --check` shows where. If your session has no target, Hyprland's `exec-once = copland-box` does the same job with your session's environment.

The package is Linux only (x86_64 and aarch64). Releases have tarballs for both and a macOS app (see "Getting it").

### Building the box

For working on it, the same flake has a dev shell with GPUI's libraries and `LD_LIBRARY_PATH` set. It brings no Rust toolchain, so cargo is whatever is on your PATH and builds inside and outside the shell share `target/`. nixpkgs is pinned to a rev in the flake itself, and `flake.lock` holds the hash. A binary from `target/` finds its libraries only inside the shell; the package above is the one that runs anywhere.

```sh
cd daemon
nix develop -c cargo build -p copland-box --release   # target/release/copland-box
nix develop -c ./target/release/copland-box --demo
nix develop -c cargo test --workspace
nix develop -c cargo clippy --workspace --all-targets -- -D warnings
```

The package doesn't run the tests: some of the box's read the web app's sources, which are outside its source on purpose. Besides `themes.css` (above), `scene.rs` and `view.rs` read `src/features/wired/scene.ts` and `WiredPane.tsx` with a small arithmetic reader (`box/src/webts.rs`) and check the port against them: every number constant, the eight wires' ends, dips and lengths at a few points of the sway, where beads rest, and the lists' width budgets at the web's scales. They fail naming what differs, and on a new web constant the box doesn't port yet. The box's padding and its zoom are its own and aren't checked.

GPUI is `gpui = "=0.2.2"` from crates.io, the newest published release. Everything under it comes from crates.io too, so that line and `Cargo.lock` pin the whole graph; no git dependencies. Pins move only when something forces it (see AGENTS.md).

### Cutting a release

Releases come from `.github/workflows/box-release.yml`, on a pushed tag `box-vX.Y.Z`:

1. Bump `version` under `[workspace.package]` in `daemon/Cargo.toml` (the box and the CLI both take it from there), run `cargo build` so `Cargo.lock` follows, and commit.
2. `git tag box-vX.Y.Z` on that commit and `git push origin box-vX.Y.Z`.

The workflow first checks the tag against `cargo pkgid` for the three binaries and stops if they differ. Then, side by side: release builds on `ubuntu-24.04` and `ubuntu-24.04-arm` (with GPUI's build libraries from apt), one on `macos-14` with Xcode 15.4 selected (GPUI's build script compiles its Metal shaders with `xcrun metal`, which the command line tools alone don't have), and `nix build` of `./daemon#deps` and `./daemon` on both Linux runners, pushing the package, and on x86_64 the deps too, to Cachix. Each build checks `--version` on each binary (the tray's on Linux only). When all of that passes it makes the release with the files, `SHA256SUMS`, and notes from `daemon/release/notes.md`. Rust is pinned in the workflow (`RUST_TOOLCHAIN`) and every action to a commit.

Running the workflow by hand (Actions, box-release, Run workflow) is a dry run: everything is built and packaged and kept as the run's artifacts, but no release is made and nothing is pushed to Cachix, unless you tick "push_cache", which pushes the Nix builds without a release. Give it a tag to check the version against, or nothing.

The packaging is plain scripts in `daemon/release/`, so it can be tried on a laptop: `check-version.sh [tag]`, `package-linux.sh VERSION ARCH target/release OUT` (needs `rsvg-convert` or `resvg`, e.g. `nix shell nixpkgs#resvg -c …`), `package-macos.sh` (on a Mac), and `notes.sh`. `copland-box.desktop` and `copland-tray.desktop` there are also what the flake installs, so the launchers can't drift.

The tray's icons are there too: `tray-icons.sh` writes the mark in four states, `tray/<state>.svg` and `tray/<state>/<size>.png` at 16, 22, 24, 32, 48 and 64 pixels, all checked in. `idle` is the plain mark, `working` has a `green` badge (a run going), `needs` an `orange` one (an agent needs you, or a last run failed), and `stopped` (no daemon answers the socket) is the mark in `muted`, greyed out. Every colour is a nord role read from `src/styles/themes.css` and the mark's paths come from `public/favicon.svg`, so rerun it (with `rsvg-convert` or `resvg` on PATH) after a change to either and commit what it writes. The tray embeds those PNGs with `include_bytes!` and sends them as the item's pixmaps, so it needs no icon theme and the build no SVG renderer.

One-time setup, for the Nix cache only; without it the release still happens and the Nix jobs say they skipped the push:

1. Create a public cache on [cachix.org](https://app.cachix.org), named `copland` or anything else.
2. Make a write auth token for it and add it to the repo as the Actions secret `CACHIX_AUTH_TOKEN`.
3. If the cache isn't called `copland`, set the Actions variable `CACHIX_CACHE` to its name (and use that name in `flake.nix` too).
4. Put the public signing key the cache's page shows (`copland.cachix.org-1:…`) in the `nixConfig` at the top of `daemon/flake.nix`. Done for `copland`.

## Testing it against a local Copland

Run `npm run dev` at the repo root, make an agent and a board in the app (or through `/api/agents`, `PUT /api/agents/:id/boards/:boardId` and `POST /api/tokens` with `agentId`), and point a config at `http://localhost:5173`. A stub runtime is enough to see the loop: a shell script that reads the URL and the `Authorization` header out of the MCP config file and calls `tools/call` with curl. Set `XDG_STATE_HOME` and `XDG_RUNTIME_DIR` to a scratch directory to keep its logs out of your real ones.

## Known gaps

- Two daemons on different configs that name the same agent work fine against each other (claims keep them off the same task), but each launches its own run on a restart for whatever is unread. Two on one config can't happen: the second refuses to start (One daemon per config, above).
- No backoff beyond the poll interval for a runtime that keeps failing on new items.
- A board with several repos: coding runs work in the first one.
- A launch to answer on someone else's task wakes on plain comments too, once the agent has taken part there. Two agents answering each other in one thread would keep each other going; nothing stops that yet beyond the agent marking its inbox read.
